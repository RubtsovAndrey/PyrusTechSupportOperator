Исчерпывающая архитектурная документация и спецификация для реализации ИИ-оператора на базе интеграции Pyrus API и Just AI Agent Platform
Введение и архитектурная парадигма интеграции
Внедрение автономных интеллектуальных агентов в корпоративные бизнес-процессы требует надежной оркестрации между системами управления задачами и платформами диалогового искусственного интеллекта. Исторически пилотные проекты по внедрению ИИ-технологий в крупных компаниях занимали от трех до шести месяцев, требуя сложных интеграций и длительных согласований. Однако использование специализированных enterprise-платформ позволяет сократить этот цикл до нескольких недель, обеспечивая окупаемость инвестиций (ROI) в 2,5–4 раза быстрее. Данная документация представляет собой детализированное руководство по проектированию и реализации ИИ-оператора. Решение базируется на интеграции облачной и серверной системы управления рабочими процессами Pyrus и enterprise-платформы для создания мультиагентных систем Just AI Agent Platform.   

Архитектурная парадигма описываемого проекта строится на событийно-ориентированной модели (Event-Driven Architecture). Платформа Pyrus выступает в роли инициатора событий, генерируя асинхронные вебхуки при наступлении определенных триггеров, таких как создание задачи или добавление комментария. Платформа Just AI Agent Platform выполняет роль процессора логики, который принимает входящий вебхук, извлекает контекст, маршрутизирует запрос к большой языковой модели (LLM) через внутренний OpenAI-совместимый прокси (экосистема Caila) и возвращает ответ обратно в Pyrus через REST API. Реализация подобной архитектуры требует глубокого понимания механизмов криптографической безопасности, управления состоянием сессий в изолированных средах и алгоритмов обработки сетевых таймаутов.   

Спецификация платформы Pyrus: Взаимодействие, события и задачи
Платформа Pyrus предоставляет разработчикам два основных вектора интеграции: REST API, при котором внешнее приложение инициирует запросы к системе, и механизм вебхуков, при котором Pyrus вызывает внешнее приложение через HTTP-запросы при наступлении событий. В контексте создания ИИ-оператора применяется гибридная модель. Входящий поток сообщений от пользователей обрабатывается через вебхуки, тогда как генерация ответов ИИ-агента осуществляется через REST API.   

В системе Pyrus задачи фундаментально разделяются на два типа: обычные задачи (simple tasks) и задачи по форме (form tasks). Обычная задача содержит фиксированный набор базовых полей, таких как текст задачи, заголовок и массив участников, из числа которых назначается ответственный. Задачи по форме отличаются наличием предварительно настроенного маршрута согласования (workflow) и кастомизируемого набора полей, специфичных для конкретного бизнес-процесса. Любое изменение в задаче, будь то редактирование значений полей, загрузка вложений или смена этапа, фиксируется в системе путем добавления комментария. Это означает, что ИИ-оператор должен взаимодействовать с Pyrus преимущественно через эндпоинты комментариев, анализируя их для понимания контекста и отправляя новые для выполнения действий.   

Модель данных и типы полей Pyrus
Для корректной передачи контекста задачи в LLM, ИИ-платформа должна уметь парсить и интерпретировать структуру полей Pyrus. Поля формы описываются в формате JSON и содержат уникальный номер, имя, тип, текущее значение и дополнительную информацию о правилах заполнения (например, immutable_step или required_step, указывающие, на каком этапе поле становится обязательным или недоступным для изменения).   

Информационная модель разделяет поля на примитивные и составные. Примитивные типы принимают значения стандартных типов данных. Составные типы принимают сложные JSON-объекты и требуют дополнительной обработки перед передачей в языковую модель.

Тип поля	Классификация	Описание и формат значения
text, money, number	Примитивный	Стандартные строковые или числовые значения.
date, time	Примитивный	Форматы YYYY-MM-DD и HH:mm соответственно.
due_date_time	Примитивный	Дата и время со сроком в минутах в формате YYYY-MM-DDThh:mm:ssZ.
checkmark	Примитивный	Флажок, принимающий строковые значения checked или unchecked.
multiple_choice	Составной	Множественный выбор, возвращающий массивы идентификаторов и имен выбранных опций, а также вложенные поля fields.
catalog	Составной	Справочник, содержащий catalog_id и флаг multiple_choice.
table	Составной	Табличный массив, включающий вложенные столбцы (объекты columns с parent_id).
Архитектура ИИ-бота должна учитывать эту вариативность. При трансформации JSON-дерева в текстовый промпт для LLM, алгоритм на стороне Agent Platform должен осуществлять рекурсивный обход составных полей и представлять их в читаемом формате, исключая служебные идентификаторы (такие как id или parent_id), чтобы экономить токены контекстного окна.   

Жизненный цикл вебхука и структура полезной нагрузки
Вебхук в Pyrus инициируется при попадании задачи во входящие (Inbox) учетной записи бота. Бот представляет собой технический аккаунт, добавленный в маршрутизацию формы на определенном этапе бизнес-процесса. При наступлении события сервер Pyrus формирует POST-запрос и направляет его на URL-адрес обработчика, предварительно зарегистрированный в настройках интеграции.   

Тело запроса представляет собой детализированный JSON-объект, содержащий весь необходимый контекст для работы ИИ. В корневом узле payload располагается параметр task_id, идентифицирующий задачу, и массив task, содержащий полный слепок текущего состояния тикета. Внутри объекта task находится массив comments, который представляет собой хронологическую историю диалога и системных изменений. Именно этот массив служит основным источником данных для формирования кратковременной памяти LLM-агента.   

Особое архитектурное значение имеют служебные URL-адреса, динамически передаваемые в каждом вебхуке. Параметр api_url указывает базовый адрес для REST-запросов (например, для добавления комментария), а files_url — адрес файлового хранилища для скачивания или загрузки вложений. Разработчикам строго не рекомендуется жестко кодировать эти адреса в константах приложения, поскольку они могут изменяться в зависимости от того, использует ли клиент облачную инфраструктуру (Cloud Pyrus) или локальное развертывание (Pyrus Datacenter).   

Вместе с адресами вебхук доставляет краткосрочный авторизационный токен в параметре access_token. Этот эфемерный токен валиден в течение 5 минут с момента вызова и позволяет боту немедленно отправлять ответные запросы к Pyrus Public API без необходимости прохождения полной процедуры авторизации. Это существенно снижает задержку (latency) при обработке запросов, исключая лишние сетевые вызовы.   

Криптографическая верификация и управление потоком
Безопасность интеграции обеспечивается обязательной криптографической проверкой входящих запросов. Pyrus снабжает каждый вебхук служебным заголовком X-Pyrus-Sig, который содержит цифровую подпись сообщения. Данная подпись генерируется с использованием алгоритма HMAC и криптографической хеш-функции SHA1. Алгоритм проверки на стороне Agent Platform требует перевода исходного тела POST-запроса в массив байт и вычисления дайджеста с использованием статического секретного ключа бота (security_key). Только при полном совпадении вычисленного хеша со значением заголовка система может доверять запросу и передавать данные в пайплайн ИИ.   

Надежность доставки событий в Pyrus реализуется через механизм повторных попыток (retries), управляемый заголовком X-Pyrus-Retry. Согласно спецификации, бот обязан ответить на вебхук HTTP-статусом из диапазона 2XX (обычно 200 OK) в течение 60 секунд (хотя для ресурсоемких задач рекомендуется предел в 30 секунд). Если ИИ-платформа не отвечает в заданный тайм-аут, соединение разрывается, и Pyrus инициирует вторую попытку через 61 секунду, а затем третью — через 122 секунды. Состояние попытки передается в заголовке X-Pyrus-Retry в формате дроби (например, 1/3, 2/3, 3/3). Эта архитектурная особенность критически важна для интеграции с LLM, генерация ответов которых может превышать стандартные сетевые таймауты. Для предотвращения отправки дублирующихся комментариев в задачу, процессор логики должен реализовывать паттерн идемпотентности, гарантируя, что один и тот же task_id в рамках одного события обрабатывается строго один раз.   

Спецификация REST API Pyrus: Генерация ответов и авторизация
Взаимодействие ИИ-агента с платформой после завершения генерации ответа LLM осуществляется посредством REST API. Глобальный лимит обращений к API Pyrus установлен на уровне 5 000 запросов за 10 минут на одного пользователя. Заголовки HTTP-ответа (X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset) предоставляют телеметрию о состоянии лимитов. Превышение квоты приводит к ошибке с кодом 429 Too Many Requests и возврату JSON-объекта с ошибкой too_many_requests. Система оркестрации ИИ должна корректно перехватывать данный статус и применять механизмы отложенного выполнения (exponential backoff).   

В рамках обработки сетевых взаимодействий система может столкнуться со стандартизированными кодами ошибок. Ошибка server_error свидетельствует о внутренних неполадках инфраструктуры Pyrus; invalid_credentials указывает на неверный логин или ключ безопасности; token_not_specified возникает при отсутствии заголовка авторизации; revoked_token и expired_token сигнализируют об аннулировании или истечении срока действия маркера доступа.   

Механизмы OAuth и ротация токенов
В ситуациях, когда бот не может использовать краткосрочный access_token из вебхука (например, при отложенной фоновой обработке тяжелых задач), ИИ-оператор должен запрашивать новый токен через конечную точку POST /auth. Этот метод принимает JSON с параметрами login и security_key. Если на один адрес электронной почты зарегистрировано несколько профилей, необходимо дополнительно передавать параметр person_id. Успешный ответ содержит долгосрочный access_token, который встраивается в HTTP-заголовок Authorization: Bearer <token> всех последующих вызовов.   

Архитектура системы должна учитывать сценарии принудительного отзыва токенов. Срок жизни токена ограничен, а превышение максимального числа одновременных токенов для одного аккаунта автоматически аннулирует самый старый из них. Кроме того, токен отзывается при смене ключа авторизации, изменении пароля или блокировке пользователя. При возникновении ошибки revoked_token приложение должно инициировать автоматическую повторную авторизацию (re-authentication flow) без вмешательства администратора.   

Добавление комментариев и манипуляция задачами
Для интеграции ответа LLM обратно в бизнес-процесс используется конечная точка POST /tasks/{task-id}/comments. Метод позволяет не только публиковать текстовые ответы, но и управлять статусом тикета и прикреплять файлы.   

Параметр тела запроса	Описание и функциональное назначение
text	
Базовый строковый параметр для текстового комментария.

formatted_text	
Текст с поддержкой HTML-форматирования (теги <b>, <i>, <ul>, <code>, цветовая разметка). Используется для передачи сложной, структурированной выдачи LLM (например, таблиц или выделения сущностей).

action	
Управляющий флаг статуса задачи. Принимает значения finished для закрытия задачи ИИ-агентом после успешного решения вопроса, или reopened для возврата в работу.

approval_choice	
Механизм согласования. Позволяет боту принимать решения: approved (согласовано), rejected (отклонено), acknowledged (ознакомлен), revoked (отозвано).

attachments	
Массив идентификаторов (guid или id) файлов, загруженных в хранилище, для прикрепления к комментарию.

skip_auto_reopen	
Булевый флаг, предотвращающий автоматическое переоткрытие ранее закрытой задачи при публикации комментария (по умолчанию false).

  
Если генерация ответа требует прикрепления файлов (например, сгенерированных отчетов), ИИ-агент предварительно вызывает метод POST /files/upload, передавая бинарные данные в формате multipart/form-data. В ответ сервер возвращает уникальный guid файла, который затем встраивается в массив attachments при отправке комментария. Стоит учитывать ограничение: один guid может быть использован в запросе только один раз.   

Архитектура процессора логики: Just AI Agent Platform
Just AI Agent Platform представляет собой мощную enterprise-среду для проектирования, оркестрации и масштабирования автономных ИИ-агентов. Платформа поддерживает развертывание в любых инфраструктурах (Any-cloud & on-premise) и поставляется, в том числе, в виде открытого дистрибутива на базе Helm-чартов для Kubernetes. Высокая надежность инфраструктуры подтверждается SLA 99,95%. Использование Agent Platform предоставляет бизнесу технологический стек, объединяющий визуальные инструменты проектирования (low-code/no-code) с возможностями написания сложных интеграций на языках JavaScript и Python (pro-code).   

Управление сессиями и маршрутизация триггеров
Процесс обработки данных в платформе строится на направленных графах (J-Graph), где стартовыми узлами выступают триггеры. Архитектура строго разделяет триггеры на коммуникационные и служебные (Workflow).   

Коммуникационный триггер («Сообщение») работает в контексте конкретного пользовательского канала связи. При его использовании платформа автоматически управляет состоянием сессии, историей диалога и маршрутизацией ответных сообщений клиенту с использованием встроенных функций группы Reactions.   

Однако, интеграция с Pyrus опирается на Workflow-триггер («Вебхук»). При активации этого триггера платформа запускает процесс в изолированной служебной сессии (с идентификатором вида workflow-{triggerId}). Ключевой инженерный вызов здесь заключается в том, что Workflow-сессия не привязана к клиенту и не имеет истории переписки. Интеллектуальный агент, запущенный в таком контексте, изначально изолирован от внешнего мира и работает исключительно с данными, поступившими в текущем HTTP-запросе. В результате стандартные методы ответов блокируются: функции Reactions (например, sendText) не знают, в какой канал отправить данные, а параметры блока «Агент» по автоматическому ответу игнорируются платформой. Разработчик обязан вручную извлечь полезную нагрузку из вебхука, реконструировать контекст для LLM, а затем явно инициировать исходящий HTTP-запрос (через модуль $http) для доставки сгенерированного ответа в стороннюю систему.   

Инъекция контекста и кратковременная память агента
Мостом между Workflow-сессией и большой языковой моделью выступает служебный объект AgentContext. Этот компонент позволяет сохранять структурированные данные и неструктурированные текстовые заметки в оперативной памяти текущей сессии. Данные, агрегированные в AgentContext, при активации ИИ-агента автоматически компилируются и встраиваются в системный промпт LLM, формируя ее контекстное понимание задачи.   

Разработчик использует встроенные JavaScript-функции платформы для динамического наполнения памяти. Функция addNote(text, [agentId]) позволяет добавлять текстовые строки. В контексте Pyrus скрипт должен проитерировать массив payload.task.comments и конвертировать каждую реплику в текстовую заметку (например, "Автор: Иван. Текст: Прошу обновить бюджет"), последовательно загружая их через addNote.   

Для структурированных атрибутов задачи (идентификаторы, суммы, приоритеты) применяется функция putValue(key, value, [agentIds]), сохраняющая пары ключ-значение. Если в процессе участвуют несколько узких ИИ-агентов (мультиагентная архитектура), разработчик может изолировать их память, передавая параметр agentId и тем самым предотвращая утечку контекста между разными моделями, что дополнительно снижает расход токенов. Для получения данных из памяти используются функции getNotes() и getValue(), а для сброса состояния — deleteNotes(), deleteValue() и глобальная clearContext().   

Инфраструктура Caila и безопасность LLM (Jay Guard)
Вызовы к нейросетевым моделям в Just AI Agent Platform маршрутизируются через платформу MLOps Caila. Caila предоставляет единый OpenAI-совместимый API (сервис openai-proxy), унифицирующий доступ к более чем 300 моделям от различных вендоров (включая Anthropic, YandexGPT, GigaChat, а также возможность подключения локальных весов). Конфигурация модели и авторизация производятся через секретные ключи, хранящиеся в защищенном хранилище платформы (Secrets) и передаваемые в параметре LLM_API_KEY или через директиву tokenSecret.   

В корпоративном сегменте передача содержимого рабочих задач в облачные LLM сопряжена с рисками утечки конфиденциальной информации. Архитектура платформы нивелирует этот вектор угроз за счет интеграции ML-DLP модуля Jay Guard (AI Security шлюз). Этот компонент, работающий на этапе проксирования запросов, осуществляет фильтрацию и маскирование персональных данных (PII), коммерческой тайны, а также блокирует попытки prompt-инъекций со стороны пользователей. Доступ к корпоративным базам знаний без необходимости ручной разметки документов реализуется посредством сервиса Jay Knowledge Hub, реализующего паттерн Retrieval-Augmented Generation (RAG).   

Взаимодействие через Chat API и управление состоянием
Платформа Just AI также предоставляет собственный Chat API (v1.0) для глубокой интеграции диалоговых систем в сторонние приложения. Спецификация Chat API включает методы для синхронного (POST /chatapi/{token}) и асинхронного (POST /chatapi/{token}/async) обмена сообщениями. Асинхронный метод возвращает лишь уникальный идентификатор запроса (questionId), позволяя вызывающей системе продолжить работу, не дожидаясь ответа LLM.   

Для получения асинхронных ответов применяется метод GET /chatapi/{token}/events, реализующий стратегию long polling. Метод позволяет фильтровать события по времени (ts) и соединению (cid). Платформа также поддерживает методы для извлечения истории диалога с пагинацией (GET /chatapi/{token}/client/{clientId}/history), сохранения и загрузки произвольного состояния сессии приложения (POST /chatapi/.../state), а также управления жизненным циклом доставки сообщений посредством обновления статусов (SENT, DELIVERED, READ, NOT_SENT). Знание этих интерфейсов полезно при проектировании сложных гибридных сред, где Pyrus может выступать лишь одной из множества точек касания клиента с ИИ-оператором.   

Проектирование сквозного интеграционного конвейера (End-to-End Pipeline)
Создание полнофункционального ИИ-оператора на базе представленных платформ требует построения направленного ациклического графа (DAG) обработки данных. Процесс исполнения разделяется на пять логических фаз, каждая из которых реализуется через узлы визуального редактора и встроенный JavaScript API (Pro-code).

Фаза 1: Инициация и верификация (Ingestion & Security)
При поступлении вебхука от Pyrus активируется служебная сессия workflow-{triggerId}. В первую очередь управление передается блоку пользовательского JS-кода. Сценарий обращается к функции Context.getMessageContent().payload для доступа к телу запроса и заголовкам. Выполняется расчет криптографического хеша HMAC-SHA1 от бинарного тела запроса с использованием security_key бота. Если вычисленный дайджест не совпадает со значением заголовка X-Pyrus-Sig, транзакция немедленно обрывается для предотвращения несанкционированного доступа.   

Фаза 2: Парсинг и обеспечение идемпотентности
После успешной аутентификации скрипт извлекает переменные task_id, api_url, access_token и массив comments. Для решения проблемы сетевых таймаутов и повторных доставок (Retries), встроенных в механику Pyrus, сценарий обращается к встроенной базе данных Db. Идентификатор задачи или последнего комментария используется как первичный ключ. Метод Db.get(key) проверяет наличие активной обработки. Если ключ найден, скрипт мгновенно возвращает ответ 200 OK в Pyrus, прерывая дублирующий вызов. Если нет — выполняет Db.put(key), блокируя параллельные запуски, и переходит к следующей фазе. Токен авторизации и URL сохраняются в кратковременном хранилище SessionDb для использования на этапе отправки ответа.   

Фаза 3: Инъекция контекста в память Агента (Context Hydration)
Массив комментариев Pyrus, представляющий сложную JSON-структуру с метаданными пользователей, подвергается конвертации. Цикл for перебирает элементы массива, формируя плоские текстовые строки (например, "Пользователь {author.first_name} пишет: {text}"). Каждая строка интегрируется в память LLM через последовательные вызовы AgentContext.addNote(text). Специфические системные параметры задачи (идентификаторы справочников, бюджетные лимиты) загружаются посредством AgentContext.putValue(key, value).   

Фаза 4: Оркестрация LLM (Generative Inference)
Управление передается блоку «AI-агент». Платформа автоматически конкатенирует системный промпт (задающий роль оператора поддержки), содержимое AgentContext и маршрутизирует собранный контекст через прокси Caila к выбранной языковой модели (например, OpenAI или YandexGPT). Модуль Jay Guard обеспечивает предварительную санитаризацию данных. Модель анализирует историю задачи и генерирует оптимальный технический или консультационный ответ. Результат генерации сохраняется во внутреннюю переменную платформы.   

Фаза 5: Маршрутизация ответа и финализация транзакции
На финальном этапе используется встроенный HTTP-клиент $http.post для инициации REST-запроса к инфраструктуре Pyrus.
Сценарий формирует URL из переменной api_url и пути tasks/{task_id}/comments. В конфигурацию клиента (объект headers) подставляется заголовок Authorization: Bearer <access_token>, где токен берется из хранилища SessionDb. Тело JSON-запроса содержит поле formatted_text с результатами работы LLM, а также, при необходимости, инструкцию action: "finished" для автоматического закрытия решенного тикета. После успешного сетевого вызова запись в Db помечается как завершенная, изолированная Workflow-сессия уничтожается, и процесс завершается.   

Заключение
Интеграция систем управления рабочими процессами Pyrus с диалоговым искусственным интеллектом Just AI Agent Platform формирует высоконадежный, автоматизированный и отказоустойчивый конвейер корпоративной коммуникации. Эффективность архитектуры обеспечивается симбиозом событийно-ориентированной модели вебхуков Pyrus и мощных инструментов изоляции сессий, управления контекстом (AgentContext) и MLOps-маршрутизации (Caila), предоставляемых платформой Just AI.

Строгое соблюдение спецификаций криптографической безопасности (HMAC SHA1-верификация), учет асинхронной природы обработки данных и внедрение паттернов идемпотентности на базе постоянных хранилищ (Db) гарантируют нивелирование сетевых аномалий, таймаутов и механизмов повторных попыток (retries). Внедрение подобного технологического стека не только кратно ускоряет запуск ИИ-агентов (сокращая время Time-to-Market до нескольких недель), но и обеспечивает масштабируемую, защищенную инфраструктуру для автоматизации рутинных бизнес-задач уровня Enterprise.
