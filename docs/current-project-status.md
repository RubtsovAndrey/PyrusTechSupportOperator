Коротко: основной контур уже работает от webhook Pyrus до ответа, заполнения полей,
закрытия, передачи оператору или создания нативной подзадачи. Живыми тестами подтверждены
рейтинговая подзадача и кассовый сценарий ошибки 148. При этом одна из главных ценностей
MVP — устойчивый разговор по подготовленной статье — подтверждена для сценария Z-отчёта
одной положительной, тремя отрицательными и двумя разговорными semantic-ветками. Задачи
`377186358` и `377187169` подтвердили отдельный Turn Interpreter, а `377230890` — весь
обобщённый путь: ответы статьи, Confirmation, post-close intent и Response Composer.
Solver теперь является Policy Reader и возвращает только авторизованный `contentPlan`;
агенты не выбирают действие Pyrus, а parser-слой связывает результат с текущим контрактом
и витком. После этой приёмки verbatim-вопросы переведены на детерминированную композицию:
модель вызывается только там, где действительно может улучшить текст. Способность темы
закончиться подзадачей теперь выводится из policy, поэтому ранний email и просьба «передайте
специалисту» больше не являются исключением для рейтингов. Срез `789e8b5` дополнительно
вынес извлечение свободных ответов из Solver в узкий `Open Answer Interpreter`: он может
записывать только объявленные статьёй ключи с дословной цитатой, а материальное
противоречие останавливает создание подзадачи до уточнения. Неизвестная тема больше не
получает произвольный вопрос Routing без двух реальных policy-кандидатов. Перед передачей
новый `Knowledge Query Planner` предлагает не больше двух смысловых формулировок поиска,
после чего `findOperatorKnowledge` сохраняет исходный вопрос и читает верхние кандидаты.
В новом эксперименте `Operator Evidence Selector` выбирает до трёх непрерывных цитат.
Код проверяет их источник и привязку к задаче/витку, затем изолирует Composer от остальных
материалов. Оператор видит те же цитаты рядом с черновиком. Без проверенных цитат Composer
пропускается. Это ограничение происхождения текста, а не доказательство смысловой
обоснованности ответа; живой повтор подтвердил один правильный результат и одну подмену клиента курьером.
Разбор: [`avatar-evidence-live-review-2026-09-05.md`](avatar-evidence-live-review-2026-09-05.md).

## 1. Что строится

Проект связывает:

- чат партнёра в Pyrus;
- workflow в Agent Platform;
- LLM-агентов для понимания языка и смысла разговора;
- MCP Базы знаний для поиска и чтения статей;
- детерминированный код для правил, состояния и действий в Pyrus.

Цель MVP — не универсальный автономный оператор. Первая версия должна предсказуемо
работать по небольшому числу заранее подготовленных тем и безопасно передавать всё
остальное человеку. Приоритеты в таком порядке:

1. правильно понять потребность партнёра;
2. не выдать неподтверждённый совет;
3. выполнить корректное действие в Pyrus;
4. сохранить человеку достаточный контекст;
5. только затем увеличивать долю самостоятельных закрытий.

## 2. Фактические границы MVP

### Входит

- Новые чаты тестовой формы Pyrus `2430464`.
- Тестовая форма тикетов `2454249` только как цель создания подзадач.
- Русскоязычные обращения по российским юнитам и рабочее предположение РФ, пока язык или
  подтверждённый юнит не показали обратное.
- Определение юнита через справочник Pyrus и заполнение поля только при однозначном
  совпадении.
- Определение компонента только из выбранной и проверенной ветки статьи.
- Самостоятельные ответы по разрешённым кассовым сценариям.
- Единый маршрут всех вопросов о РКО и Рейтинге стандартов: поиск ответа в разрешённых
  статьях, затем при необходимости сбор данных и создание подзадачи.
- Передача неизвестных и неподготовленных тем оператору со связной внутренней сводкой.
- Поиск возможных материалов общей БЗ и неотправленный черновик первого ответа для
  оператора при неизвестной теме.
- Защита от повторных webhook, перекрывающихся запусков, повторной отправки и дублей
  подзадач.

### Не входит

- Продуктивные формы. В частности, в тестовый `config.forms` нельзя добавлять формы
  `1165239` и `1096731`.
- Работа во входящих тикетах, включая тикеты, созданные самим ботом.
- Самообслуживание для Казахстана и других стран. Раннее продуктовое намерение охватить РФ
  и КЗ было сужено: текущие исполняемые инструкции подготовлены только для РФ.
- Анализ вложений, изображений и видео.
- Чтение и изменение карточек сотрудников, MD Audit, платёжных систем и других
  бизнес-систем.
- Онлайн-обучение на потоке обращений и автоматическая публикация новых правил.
- Автоматические ответы партнёру из любой найденной статьи общей БЗ.

### Правила языка и рынка

- Пока нет противоположного сигнала, разговор считается русским и российским. Это даёт
  право искать российский сценарий, но не даёт права угадывать или записывать юнит.
- Любой содержательный нерусский текст либо подтверждённый юнит не из `dodopizza.ru`
  ограничивает работу базовым сбором проблемы и юнита с последующей передачей оператору.
- Внешний текст всегда должен быть на языке партнёра. Если безопасный локализованный текст
  сформировать нельзя, выполняется тихая передача.
- Закрытие чата и создание подзадачи требуют подтверждённого юнита. Если проблема решена,
  но нет юнита или компонента, задача остаётся оператору.

## 3. Статус возможностей

Обозначения: **принято** — подтверждено живой цепочкой; **работает с оговорками** — есть
положительные прогоны, но остаётся существенный крайний случай; **развёрнуто, ждёт
приёмки** — контракт закреплён тестами и находится на платформе, но ещё не подтверждён
новой живой трассой; **локально** — контракт есть только в Git/тестах; **отложено** —
сознательно вне MVP.

| Возможность | Статус | Что известно сейчас |
|---|---|---|
| Белый список форм и игнорирование тикетов | принято | Неизвестные формы и роль `ticket` отбрасываются до агентов. Без внешнего `config` безопасный default знает только тестовый чат. |
| Сбор проблемы, языка и юнита | работает с оговорками; новый prompt отправлен | Юнит «Тамбов-1» и неоднозначные точки проверялись живьём; код не доверяет выдуманному моделью значению. Во втором черновике неподтверждённо сказано, что фото появится в приложении. Отбор по словам не различает объект и область применения инструкции |
| Нерусский язык / иностранный юнит | локально | Сбор и передача локализованы и покрыты тестами; полноценные страновые сценарии не реализованы. |
| Закрытие и заполнение полей | принято | `finished` выполняется только вместе с достоверными полями «Юнит» и «Компонент». Нет поля — нет автоматического закрытия. |
| Повторные и параллельные webhook | работает с оговорками | Есть дебаунс по комментарию, проверка свежего сообщения и атомарное право на подзадачу. Быстрые сообщения уже проверялись живьём, но общий `AgentContext` платформы остаётся внешним риском. |

Итоговая оценка: каркас MVP функционален, но весь MVP нельзя считать принятым, пока не
пройдёт живую приёмку каждый включённый партнёрский сценарий. Статус `approved` у источника
или статьи означает, что содержание проверено; он не заменяет живую приёмку разговора.
Обратный пример тоже есть: рейтинговый маршрут функционально принят, но поле
`validation.status` его исходника пока остаётся `testing` и должно быть приведено в
соответствие отдельной редакторской правкой.

## 4. Архитектура выполнения

### Общий поток

```text
Pyrus webhook
    ↓
receiveWebhook
    ├─ фильтр формы, автора и повторного комментария
    ├─ ранние детерминированные исходы:
    │  просьба человека / вложение / точная благодарность / закрытие
    ├─ прочий текст после закрытия → конечный контракт gratitude_only|other
    └─ восстановление state:<taskId> и стадии разговора
        ↓
Intake Agent → проверка и сохранение фактов кодом
        ↓
Routing Agent → локальный каталог → при необходимости MCP-уточнение
    ├─ нет подтверждённой темы → Knowledge Query Planner (≤2 вариантов)
    │                           → кодовый MCP-поиск и чтение выбранных статей
    │                           → Operator Assist Composer → внутренняя заметка и handover
    └─ уточнение допустимо только между ≥2 реальными policy-кандидатами
        ↓
Solver / Policy Reader → один активный узел статьи или разрешённая внешняя статья
        ↓ авторизованный responsePlan
Composition boundary
        ├─ verbatim=true → дословный текст policy без LLM
        └─ прочий план → Response Composer без изменения решения
        ├─ защищённый вопрос успешно доставлен
        │       ↓ следующий webhook
        │  Turn Interpreter → проверка frame → searchKnowledge применяет policy
        ├─ открытый вопрос статьи успешно доставлен
        │       ↓ следующий webhook
        │  Open Answer Interpreter → дословные evidence и разрешённые ключи
        │       ├─ материальное противоречие → один уточняющий вопрос
        │       └─ согласованные факты → Solver читает следующий policy-шаг
        ↓
Turn Interpreter по контракту Confirmation → resolved / failed / question / unclear
        ↓
summary-агент при handover или подзадаче
        ↓
applyOutcome → pendingOutcome
        ↓
finalize → внутренняя заметка, ответ партнёру, поля, approval или finished

Отдельный побочный выход: createSubtask создаёт нативную подзадачу Pyrus.
```

Граф намеренно ацикличен. Возврат к статье происходит не обратным ребром, а следующим
webhook партнёра и сохранённой стадией. Это решение появилось после живого инцидента, где
циклический workflow вызвал десятки повторов solver/finalize, несколько сообщений после
передачи и запуски длительностью более 100 секунд. Тест графа теперь запрещает любой цикл.

### Разделение ответственности

| Слой | Отвечает за | Не имеет права |
|---|---|---|
| Intake Agent | язык, суть проблемы, извлечение слов партнёра о юните и добровольного email | выбирать тему, давать решение, угадывать юнит |
| Routing Agent | выбрать только кандидата, возвращённого инструментами, или один раз различить вопросом минимум две реальные темы | придумывать тему, произвольное уточнение, действие Pyrus или компонент |
| Knowledge Query Planner | предложить до двух переформулировок исходной неизвестной проблемы для повышения полноты поиска | отвечать партнёру, называть неупомянутые продукты/роли, выбирать статью, маршрут или действие |
| Turn Interpreter | сопоставить текущую реплику с конечными `value` одного контракта: ответ статьи, Confirmation или post-close intent; процитировать доказательство | вызывать MCP/tool, давать совет, выбирать `go`, следующий шаг, компонент или действие |
| Open Answer Interpreter | извлечь из текущей реплики только объявленные свободные поля статьи с дословным evidence; заметить материальное противоречие | читать policy, добавлять ключи, выбирать исход, создавать подзадачу или отвечать партнёру |
| Solver / Policy Reader | прочитать выданный шаг или allowlist-источник и подготовить внутренний `contentPlan` | писать финальный текст, придумывать совет, самовольно менять тему или бизнес-исход |
| Composition boundary / Response Composer | дословно материализовать защищённый вопрос кодом либо естественно сформулировать прочий привязанный к витку `responsePlan` | читать policy, вызывать tools, менять тип ответа, действие, факты или канонический вопрос |
| Operator Evidence Selector | выбрать до трёх дословных цитат из текущих прочитанных кандидатов | придумывать источники и цитаты, менять маршрут, выполнять действия |
| Operator Assist Composer | подготовить внутренний черновик только по исходному вопросу и проверенным выбранным цитатам | читать отброшенные материалы и переписку, создавать черновик без доказательств, отправлять текст партнёру, добавлять URL или факты из памяти, менять маршрут и действие |
| Summary Agents | связно пересказать оператору или в подзадачу проблему словами партнёра | менять маршрут и добавлять собственные факты |
| Детерминированные функции | валидация фактов, статьи и ветки; права на ответ; состояние; идемпотентность; действия Pyrus | свободно интерпретировать естественный язык |
| Статья политики | тема, вопросы, компоненты, разрешённые источники, шаги и конечный исход | выполнять HTTP-действия и обходить общие предохранители |

В текущем тестовом профиле `Operator Evidence Selector` — обычная функция, вызывающая
Terra через `Llm.sendRequest` без tools (`1000299722-open_ai_gpt56terra-swl`, лимит 8192).
Все 10 agent-узлов используют GPT-4.1-mini. Agent-вызов Terra отклонён провайдером;
явный вызов функции ещё ждёт живой проверки. Решения не должны зависеть от того, что модель обязательно
вызовет нужный инструмент: критические переходы либо выполняет сам граф, либо результат
модели перепроверяет код.

### Состояние разговора

Для каждого чата используется документ `state:<taskId>`. В нём разделены:

- `data`: подтверждённые факты и состояние статьи — юнит, компонент, тема, email, суть,
  ответы на вопросы, попытки, текущий узел;
- `runtime`: данные только текущего webhook — токен, URL Pyrus, канал, id комментария и
  найденные id полей;
- `pendingOutcome`: подготовленное, но ещё не доставленное решение витка;
- маркеры идемпотентности: `lastProcessedCommentId`, `internalNotePostedFor`,
  `subtaskRequestKey`, `subtaskClaim`, `subtaskId`.

`finalize` — единственная обычная точка записи в существующий чат Pyrus.
`createSubtask` — единственное отдельное побочное действие. Стадия сдвигается только после
успешной доставки. Более свежая реплика партнёра отменяет отправку устаревшего ответа, но
не должна стирать уже подтверждённые факты.

### Действия в Pyrus

- Ответ партнёру всегда отправляется через его внешний `channel`.
- Внутренняя сводка отправляется без `channel` и поэтому видна оператору, а не партнёру.
- Handover выполняется через утверждение на следующий этап.
- Успешное завершение выполняется через `action: finished`, без перевода по этапам.
- Подзадача создаётся с `parent_task_id`; поле `95` не используется.
- Номера полей формы не захардкожены как основной путь: они ищутся по именам в описании
  конкретной формы.
- Markdown-ссылки в чате Pyrus визуально не скрывают URL. Поэтому проверенная ссылка
  отправляется как HTML в `formatted_text`; при однозначном HTTP 400 выполняется один
  plain-text fallback. `text` и `formatted_text` одновременно не отправляются.

## 5. Архитектура знаний и роль MCP

### Два вида знания

1. **Политика обработки** хранится в нашем пространстве «ИИ Техподдержка — Конфигурация».
   Она определяет, когда тема подходит, что спросить, какой компонент поставить, можно ли
   отвечать, создать подзадачу или передать оператору.
2. **Предметное знание** хранится в обычных статьях нашей или общей БЗ. Оно даёт факты и
   инструкции, но само не разрешает закрытие, подзадачу или другой бизнес-исход.

Это принципиальное разделение: релевантная статья общей БЗ не становится исполняемым
процессом только потому, что хорошо нашлась.

### Источник правды и сборка

Редактируемый источник подготовленных тем находится в
`docs/knowledge/topics/*.json`. Производные файлы нельзя править вручную:

```text
docs/knowledge/topics/*.json
    ↓ node tools/build-knowledge.js
docs/knowledge_catalog.json     — runtime-снимок для документа БД
docs/knowledge-manifest.json    — хеши и соответствие файлов
docs/rag/*.md                   — публикуемые представления статей
```

На текущий момент публикация статей, загрузка `knowledge_catalog` и обновление
`unitCatalog` остаются ручными. Это сознательная статичная схема MVP: реальные обращения
служат материалом для анализа и регрессий, но не меняют правила без проверки владельцем.

### Как используется MCP

Платформенный `rag.mode` намеренно оставлен `off`. MCP используется напрямую и выполняет
три разные задачи:

1. **Уточнение темы.** Если локальный каталог не дал уверенного ответа, Routing Agent может
   сделать до двух поисков в нашем policy-пространстве: исходной фразой и затем коротким
   запросом «объект + симптом» словами партнёра. Принимается только опубликованный
   `agent-topic/1`, чей полный машинный блок совпадает с текущим runtime-каталогом.
2. **Ответ по разрешённому источнику.** Выбранная policy-статья задаёт allowlist конкретных
   статей. MCP находит и читает их, а Solver отвечает только найденными фактами. Разрешение
   на партнёрский ответ действует для одного текущего комментария и не переиспользуется.
3. **Подсказка оператору.** Если подготовленной темы нет, `Knowledge Query Planner` без
   tools предлагает максимум две смысловые формулировки. Код сохраняет исходный запрос,
   ищет сначала в support-пространствах, при необходимости расширяет область и читает до
   трёх выбранных статей. Только после этого `Operator Assist Composer` может подготовить
   внутренний черновик. Без статьи он принудительно равен null. Ссылки и черновик не
   получают `channel`, а недоступность MCP или сбой агента не мешают handover.

В интерфейсе БЗ замечено, что часть запроса после запятой может отбрасываться. Поэтому
машинные поисковые запросы нормализуют запятые в точки и не строят смысл на хвосте после
запятой.

В MCP-коннекторе нет доступного проекту аналога `CiteSources`. Источники контролируются
иначе: policy хранит проверенные `spaceId/articleId/updatedAt`, модель не имеет права
вставлять свой URL, а `finalize` прикладывает одну ссылку, построенную из реально
прочитанного разрешённого источника.

## 7. Подтверждённые достижения

### Безопасность и управляемость

- Продовые формы исключены не договорённостью, а входным whitelist.
- Общая БЗ не может самовольно разрешить партнёрский ответ.
- Компонент нельзя придумать: принимается только значение активной статьи.
- Чат нельзя автоматически закрыть без юнита, компонента и id соответствующих полей.
- Переоткрытый чат не запускает новую автоматическую тему и молча уходит человеку.
- Вложения не интерпретируются моделью.
- Сырые URL модели удаляются; источник добавляет детерминированный слой.
- Направленные циклы в графе запрещены автоматической проверкой.

### Живые продуктовые результаты

- Рейтинговый сценарий прошёл от вопроса и чтения БЗ до добровольно присланного email,
  единственной подзадачи, заполнения полей и закрытия родительского чата.
- Подзадача видна в штатном поле связанных задач Pyrus; отдельный id чата в поле формы не
  потребовался.
- Ошибка 148 была распознана по описанию «неверная длина реквизита», то есть MCP уже
  используется не только как поиск буквального кода ошибки.
- Случайная ссылка из буфера не считается иностранным языком и не получает ложную причину
  «партнёр написал в закрытый чат».
- Быстрое следующее сообщение партнёра не приводит к отправке уже устаревшего ответа.
- HTML-ссылка в рейтинговом ответе отображается словом «Ссылка»; транспортный отказ
  `formatted_text` обрабатывается безопасным одиночным fallback.
- Для неизвестного вопроса общий поиск БЗ умеет оставить оператору полезную статью и не
  показать её партнёру; слабые совпадения отбрасываются.

| РКО с прямой передачей / `377299570` | `30/39`, FAIL | Первый ответ верен; второй виток аварийно передан оператору вместо сбора и подзадачи |

В обоих avatar-чатах Query Planner выполнил свою задачу: вариант «как изменить фотографию
курьера» вернул статью `a13f90e0-6f24-45ba-b7af-9c21a387ff3a` первой. Дефект расположен
после MCP. `findOperatorKnowledge` до чтения требует буквального совпадения слов запроса с
заголовком или коротким поисковым excerpt. У точной статьи заголовок — про личную карточку
сотрудника, а excerpt — про хранимые данные; нужные слова находятся глубже и поэтому статья
не допускается до `search_in_content`. Дополнительно безусловный приоритет собственного
пространства ставит слабое `[CASH]`-совпадение выше support-статьи. Вариант «смена
изображения курьера» особенно наглядно спутал изменение фотографии с кассовой сменой.

Это привело не только к неполной выдаче. В первом чате черновик верно назвал карточку
сотрудника, но приложенные источники не подтверждали инструкцию достаточно прямо. Во
втором черновик снова предложил выяснять «курьерское приложение или другую систему», а
ссылки вели на установку приложения и операции с заказами. Черновики остались внутренними,
поэтому внешняя safety-граница выдержана, но цель полезной помощи оператору не достигнута.

В рейтинговом чате Interpreter правильно классифицировал просьбу о прямом контакте как
`failed`, а policy подготовила вопрос о результате и email. Solver вернул допустимый по
смыслу `contentPlan`, но в виде массива. `parseAgentJson` преобразует в `responsePlan`
только строковый `contentPlan`, поэтому очистка контекста и публикация плана не произошли.
Response Composer увидел старый confirmation-контракт, вернул его id и повторил уже
отвергнутый совет. `parseResponseComposition` остановил stale/incomplete plan, после чего
safety-ветка корректно, но преждевременно передала чат оператору. Это дефект нормализации
контракта в нашем коде, проявленный вариативностью ответа модели; смена модели сама по себе
его надёжно не устраняет.

Z-чат, напротив, подтвердил основной замысел смысловых контрактов. Interpreter понял
«не печатали на этой», короткое «да», подтверждение «да супер» и post-close благодарность
«ага спасибо»; protected-вопросы прошли без Composer, совет — через Composer и validator,
задача закрылась и не переоткрылась. Формальный FAIL означает лишь, что ручной прогон
использовал не четыре строки из `messages` сценария. Для анализа смысла это полезная
вариация, но как точное воспроизведение эталона такой прогон не считается.

## 9. Частые сложности и системные вызовы

### 9.1. Естественный язык против строгих веток

Главная продуктовая сложность — не поиск точного ключевого слова, а сохранение смысла в
разговоре: отрицания, порядок слов, короткие ответы, поправки и добровольно присланные
данные. Нельзя перечислить в коде все фразы, но и нельзя полностью доверить ветку модели.
Рабочий компромисс: модель извлекает смысл, статья задаёт допустимые варианты, код проверяет
активный вопрос, свежесть ответа и безопасный конечный переход.

### 9.2. Универсальность против hardcode

Код не должен знать про ошибку 148, Z-отчёт или конкретный рейтинг. В нём допустимы только
универсальные понятия: обязательный признак, исключение, активный вопрос, свежий ответ,
безопасная развилка, следующий шаг, handover и terminal. Конкретные признаки, вопросы,
компоненты и решения должны жить в статье. Исправление одного живого кейса считается
хорошим только тогда, когда улучшает общий механизм либо явно дополняет предметное знание
статьи.

### 9.3. Нестабильность LLM

Живые прогоны уже показывали пропуск tool-вызова, два JSON-объекта подряд, пустой summary,
выдуманный совет, неверную классификацию ответа и строку/массив для одного логического
поля. Поэтому модель не является владельцем бизнес-перехода. Parser выбирает последний
валидный объект, разрешение на решение выдаётся инструментом на один комментарий, а
терминал статьи имеет приоритет над прозой модели. Контракты Agent Platform сейчас
задаются prompt-ом (`structured-output-schema: null`), поэтому очевидные эквивалентные
формы нужно либо нормализовать на границе, либо отклонять с детерминированным продолжением,
а не надеяться, что более сильная модель никогда не изменит форму JSON.

### 9.4. Конкурентные webhook

Партнёр может отправить следующее сообщение до окончания предыдущего запуска. Нормальное
время отдельных живых витков после удаления циклов было примерно 5–20 секунд, поэтому это
не редкий крайний случай. Свежесть проверяется непосредственно перед записью в Pyrus.
Отдельный нерешённый риск — общий `AgentContext` на уровне trigger: параллельные чаты могут
теоретически влиять на контекст agent-узлов, хотя факты и действия хранятся раздельно по
`taskId`. Нужен специальный нагрузочный тест двух разных чатов в одну секунду.

### 9.5. Внешнее состояние вне Git

Репозиторий не содержит актуальные документы БД `config`, `knowledge_catalog` и
`unitCatalog`, а также фактический статус публикации и индексации статей. Код одного коммита
может работать с каталогом другого. Перед каждым живым тестом нужно сверять:

- whitelist форм и `knowledgeExecution`;
- `subtaskFormId`;
- хеш/версию загруженного `knowledge_catalog`;
- актуальность `unitCatalog`;
- публикацию policy-статьи и даты allowlist-источников.

По факту последних живых ответов тестовый чат работает в режиме `partner_answer`, но это
значение находится в БД и не доказывается содержимым Git. Репозиторный fallback остаётся
`handover_only`.

Интеграция Terra `1000299722-open_ai_gpt56terra-swl` уже имеет отдельный YAML в репозитории
с моделью `just-ai/openai-proxy/gpt-5.6-terra`. Agent-подключение в `c0c0fcb`
не прошло smoke из-за служебного switchToState. В `aa85343` подготовлен явный вызов без
инструментов; требуется повторная проверка адаптера;
профиль и откат описаны в [`terra-selector-test.md`](terra-selector-test.md).

### 9.6. Ограничения Agent Platform и Pyrus

- Экспорт Agent Platform удаляет `docs/`, `tests/` и `tools/`; обычный ручной merge может
  потерять всю инженерную часть проекта.
- Параметры платформенных функций неизменяемы, а поддерживаемый JavaScript уже локального
  Node.js.
- Некоторые массивы и сочетания родительских/дочерних путей в точечной записи БД вызывают
  ошибки MongoDB.
- Pyrus при non-2xx не всегда даёт коду тело ответа, поэтому транспортную причину приходится
  восстанавливать по собственным логам.
- Agent Platform не экспортирует в трассе последний raw-ответ модели. Его результат часто
  можно увидеть только по последующему вызову функции.
- Молчание партнёра не имеет таймера: без внешнего планировщика чат остаётся в
  `awaiting_*` бессрочно.

### 9.7. Semantic retrieval против лексического safety-фильтра

MCP ранжирует по смыслу, но не возвращает численный relevance score. Наш текущий фильтр
пытается защититься от шума совпадением слов только по заголовку и короткому excerpt. В
результате он может отбросить лучший semantic hit до чтения содержимого и одновременно
пропустить статью по многозначному слову. Следующий безопасный порядок: ограниченно
прочитать несколько верхних результатов каждого хорошего варианта, проверить релевантность
по найденному внутри фрагменту, затем дедуплицировать и ранжировать. Собственное техническое
пространство не должно получать абсолютный бонус для неизвестной темы: его уже проверил
основной catalog/router. Нужны отдельные метрики `recall@k` точной статьи и precision
показываемых оператору материалов.

### 9.8. Ручной live-run и точность отчёта

`read-trace` правильно считает отличившуюся реплику нарушением сценария: иначе нельзя
доказать воспроизводимость конкретного теста. Но общий `FAIL` сейчас не различает input
drift и дефект поведения. Поэтому в выводе всегда нужны две оценки: формальная по
`tests/live/scenarios.json` и продуктовая по фактически пройденным границам. Для строгой
регрессии реплики нужно копировать из `--list-scenarios`; свободные формулировки лучше
сохранять как отдельный semantic-вариант, а не молча подменять ими существующий сценарий.

## 10. Принятые архитектурные решения

Эти решения не следует пересматривать при каждом новом кейсе без отдельной причины:

1. **Статичный MVP.** Знания меняются через редакторский цикл и ручную валидацию, а не через
   автоматическое обучение на живом потоке.
2. **Чат — единственный вход.** Тикет является только создаваемой подзадачей.
3. **Тема стабильна в одном непрерывном чате.** До уверенного выбора агент любопытен и может
   уточнять; после выбора новые детали дополняют текущую тему. Переоткрытие принимает
   оператор.
4. **MCP дополняет, но не заменяет policy.** Поиск может найти кандидата или факты, но не
   дать право на бизнес-действие.
5. **`rag.mode=off` — сознательное решение.** Прямой MCP сейчас полезнее и управляемее
   платформенного RAG.
6. **Fail closed.** Нет подтверждённой статьи, ветки, рынка, юнита или компонента — нет
   автоматического закрытия или непроверенного совета.
7. **Бизнес-правила принадлежат статьям.** Движок исполняет общий формат, а не коллекцию
   специальных `if` под известные обращения.
8. **Все side effects централизованы.** Обычные записи делает `finalize`, подзадачу —
   `createSubtask` с отдельной идемпотентностью.
9. **Сводка — пересказ сути, не набор обрывков.** Структурированные точные ответы остаются
   в состоянии для маршрутизации, а человеку передаётся цельная проблема словами партнёра.
10. **Локальные тесты плюс обязательный живой прогон.** Ни один из этих уровней не заменяет
    другой.

## 12. Практический порядок работы

### Перед изменением

1. Прочитать этот документ и соответствующий раздел [`project-map.md`](project-map.md).
2. Проверить `git status` и последний коммит.
3. Если дефект найден в живом чате, сначала разобрать цельные трассы:

   ```bash
   node tools/read-trace.js "/полный/путь/к/папке" --prompt
   ```

4. Отделить продуктовую ошибку от ошибки модели, движка статьи, платформы и транспорта
   Pyrus.

### При изменении знания

Править только `docs/knowledge/topics/*.json`, затем:

```bash
node tools/build-knowledge.js
node tools/build-knowledge.js --check
node tests/run.js
```

Нужно просмотреть дифф исходника, сгенерированного каталога, RAG-документа и манифеста.
Затем тот же `knowledge_catalog` вручную загрузить в документ БД и при необходимости
опубликовать/переиндексировать статью в БЗ.

### При изменении кода или графа

Минимальная проверка:

```bash
node tests/run.js
git diff --check
```

После коммита деплой выполняется только так:

```powershell
pwsh tools/deploy.ps1
```

Скрипт получает экспорт платформы, восстанавливает защищённые каталоги, проверяет удаления,
запускает тесты и пушит `main`. Обычный `git push` без последующего контроля экспорта
опасен потерей документации и тестов.

### После деплоя

1. Новый сценарий проводить в новой тестовой задаче, чтобы не наследовать `state:<taskId>`.
2. Проверять глазами партнёрский текст, внутреннюю сводку, поля, этап и связку подзадачи.
3. Выгружать все трассы разговора в отдельный каталог, не добавляя их в Git.
4. Проверять трассу через `tools/read-trace.js` и переносить значимые живые случаи в
   регрессии.
