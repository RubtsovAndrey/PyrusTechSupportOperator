**Обновление 2026-09-04, первый семантический контракт ответа.** Трассы задач `377168487`
и `377169806` показали, что Solver уже понимал разговорные формулировки «закрыта», «смена
открыта сказал кассир» и «открывается», но защитный движок пропускал ветку только при
совпадении со словарём `when`. Добавление новых фраз не устраняет класс ошибки, поэтому
шесть защищённых развилок Z-статьи переведены на конечные `value` и описания `meaning`.
Solver сообщает только смысл текущей реплики, `activeQuestionId` и дословный
`evidenceText`; `searchKnowledge` проверяет, что вопрос действительно доставлен и всё ещё
активен, значение разрешено статьёй, цитата присутствует в текущем сообщении, а ответ не
содержит явной неуверенности и не противоречит высокоточному детерминированному признаку.
Следующий узел, совет и конечное действие остаются исключительно в `go` статьи.

Вопрос становится активным только после успешной отправки через `finalize`; значение
нельзя применить к подготовленному, недоставленному или устаревшему вопросу. Точные
реплики и конечные значения сохраняются раздельно для диагностики. Старые статьи и их
лексический fallback остаются совместимыми. Формулировки из живых сбоев закреплены
сквозными тестами без добавления в `when`; полный локальный прогон: `ALL 1157 CHECKS
PASSED`. После деплоя кода остаются ручная публикация `knowledge_catalog` и живая приёмка.
Смысловая классификация благодарности после закрытия — следующий отдельный срез.

**Обновление 2026-09-04, приёмка и стабилизация Z-сценария.** Четыре живых диалога
`377152359`, `377152968`, `377153482`, `377153964` подтвердили полный успешный путь и три
отрицательных исхода: открытая смена, более поздний фискальный документ и недоступный Тест
драйвера ККТ. Во всех отрицательных случаях непроверенная инструкция осталась внутри
защитного контура, поля и компонент были корректны, задача перешла первой линии.

Разбор выявил два системных нюанса. Pyrus помечает благодарность после `finished` как
`action: reopened`; общий reopen имел приоритет над уже существующим узким классификатором
благодарности и будил оператора. Теперь чистое «спасибо» проверяется первым и закрывает чат
повторно, а благодарность вместе с новым вопросом по-прежнему передаёт тред человеку.
Summary-агент во всех трёх отрицательных ветках вместо JSON сразу вызвал платформенный
`switchToState` с пустым content. Известные терминалы теперь содержат декларативную
`handoverReason`; при наличии проблемы и причины граф пропускает advisory summary-модель и
строит операторскую заметку детерминированно. Служебные evidence-поля больше не считаются
отдельными ответами в логе. Полный локальный прогон: `ALL 1144 CHECKS PASSED`.

**Обновление 2026-09-04, разговорные ответы в безопасной кассовой ветке.** Трасса задачи
`377128708` из `040926_big_z_problem` показала, что статья верно доводит партнёра до печати
копии Z-отчёта, но не понимает короткое «нет» про более поздние фискальные документы:
Solver мог записать его как ответ на будущий вопрос о Тест-драйвере, а канонический вопрос
повторялся несколько раз. Теперь короткая контекстная реплика может заполнить только ключи
последнего действительно доставленного вопроса, активному узлу показываются только его
неотвеченные поля, а последовательные бинарные проверки требуют отдельного сообщения
партнёра. Прямые «да/нет» объявлены самой статьёй; ответы с оговорками вроде «вроде да»
по-прежнему не считаются безопасным подтверждением.

У неоднозначной обязательной развилки появился привязанный к комментарию лимит: один раз
статья переспрашивает, после второго неясного ответа передаёт чат оператору вместо цикла.
Если после инструкции печати партнёр сообщает, что галочка «Включено» не ставится или
пропадает, статья не выдаёт новую непроверенную инструкцию партнёру, но прикладывает к
операторской сводке уже проверенную теневую рекомендацию о соединении ККМ. При сбое
summary-модели запасная «Суть» теперь предпочитает свежий текст неудачи прежнему короткому
ответу на диагностический вопрос. Сквозные тесты повторяют разговор
`да → нет → да → галочка не ставится` и ошибочную запись ответа в будущий ключ. Полный
локальный прогон: `ALL 1127 CHECKS PASSED`.

**Обновление 2026-09-04, восстановление прерванного MCP-поиска и безопасные вопросы
кассовой статьи.** Трассы задач `377118078` и `377121831` из `040926_no_z_paper`
показали два независимых сбоя. После остановки платформенного запуска новый вопрос «Вы
тут?» вытеснял из MCP-запроса уже собранный точный симптом. Теперь разрешение на
уточнение маршрута хранит снимок содержательных слов партнёра; при восстановлении он и
сохранённые ответы статьи имеют приоритет над новой служебной репликой и ранней общей
формулировкой. Части поискового запроса разделяются точками, а запятые нормализуются,
поскольку реальный интерфейс БЗ может отсекать хвост после запятой.

Во втором чате Solver вернул два JSON-объекта подряд, старый жадный разбор склеил их и
ошибочно включил защитную передачу оператору. Parser теперь выделяет сбалансированные
объекты с учётом строк и берёт последнее валидное исправление модели. Для узлов статьи с
`requireBranchEvidence: true` неоднозначный ответ больше не разрешается приблизительной
веткой: код повторяет ровно канонический вопрос статьи, привязанный к текущему комментарию.

## Самое главное в двух абзацах

MVP работает только в **чатах тестовой формы** `2430464`. Форму `2454249` он использует
только как цель создания подзадач; входящие тикеты не обрабатывает. Каталог ограничен пятью заранее
подготовленными темами, а любые остальные обращения собираются и передаются оператору с
необязательной внутренней подсказкой из общей БЗ.

Код и статические проверки готовы к сквозной приёмке. Самый важный незакрытый риск — не
логика маршрута, а внешняя связка: реальная модель → опубликованная policy-статья → четыре
источника MCP → поля тестовой формы `2454249` → связь с родительским чатом. Продовые формы
в тестовый проект не подключаются вообще.

## Что изменилось в этот заход: плавность разговора

Разбор начался с того, что появился **симулятор разговора** (`tests/dialog.js`, отчёт —
`tests/dialog.check.js`): витки идут через настоящий граф и настоящие функции, подставлены
только Pyrus, база знаний и модель, причём модель подставлена «образцовым агентом», который
делает буквально то, что велит промпт. Логика такая: если разговор спотыкается при идеально
послушной модели, виноват не промпт, а граф или код. До этого каждый такой дефект по
отдельности выглядел как «модель ошиблась» и находился у партнёра.

Нашлось и исправлено семь вещей. Шесть из семи — **не про модель**, а про то, что у бота
не было понятий, без которых разговор не может идти гладко.

1. **«Это не ответ на мой вопрос».** Главная находка: «партнёр не ответил» и «партнёр сказал
   совсем другое» были для кода одним и тем же. Возражение «хватит вопросов, позовите
   оператора» засчитывалось как отказ отвечать, дерево прыгало в терминал `subtask`, и первая
   линия получила бы тикет «поменять телефон» без сотрудника, без номера и без причины. Дело
   не в слове «оператор» — так же выглядит уточняющий вопрос, смена темы и «сейчас узнаю у
   управляющей». Признак теперь один и считается кодом: добавил ли виток статье хоть один
   ответ. Ответ на ЧАСТЬ вопросов по-прежнему двигает статью — поля необязательные.
2. **Просьба человека слышна на любой стадии.** Проверка жила в промпте intake, а
   `awaiting_answers` / `awaiting_email` / `awaiting_confirmation` уходят в solver,
   createSubtask и confirmation напрямую. То есть бот не слышал просьбу ровно там, где
   ветвящаяся статья проводит большинство витков.
3. **Вопрос про сам совет.** `unclear` в `nextSolutionStep` уводит обращение человеку — это
   решение осознанное («не смогли прочитать ответ — пусть посмотрит человек»), но `unclear` —
   ровно то, что модель возвращает на «а где эту крышку искать?». Появился статус `question`:
   тот же шаг выдаётся снова, попыткой не считается.
4. **Благодарность в закрытый чат.** Ветка `end: close` закрывает чат сразу после совета, и
   «спасибо» приходило уже как переоткрытие — то есть уезжало оператору. Защита переоткрытых
   чатов сохранена целиком: снят ровно случай, когда в сообщении нет ничего, кроме
   благодарности.
5. **Язык.** «Пишет не на русском» перестало быть поводом для эскалации, всем агентам велено
   отвечать на языке собеседника. Ограничение записано в `control-points.md`: на язык
   партнёра переходит только речь модели, фразы кода остались русскими.
6. **`scope: "network"` был мёртв на практике.** Ветку «запрос от всей сети» умел только
   `matchUnit`, а выгрузка живого чата показала, что flash-модель инструмент **не вызывает
   вовсе** (ноль вызовов на семь обращений к модели) — юнит опознаёт запасной путь в
   `parseAgentJson`, который про сети ничего не знал. Партнёра трижды спрашивали номер точки,
   которого не существует. Теперь то же правило есть и в запасном пути.
7. **«Закройте чат» означает закрытие, а не передачу.** На вопросе статьи сообщение сразу
   попадало в solver: модель отвечала «обращение закрываю», но управляющим результатом
   возвращала `handover`, поэтому Pyrus делал обратное услышанному. Явная просьба закрыть
   именно текущий чат, обращение, заявку, задачу или тикет теперь распознаётся кодом на любой
   рабочей стадии и завершается без вызова модели. Голого слова «закрыть» недостаточно —
   «закройте крышку кассы» и отрицание «не закрывайте чат» остаются обычными сообщениями.

Побочно, но важно: **ключ статьи убран из подбора по словам.** Ключи латиницей
(`pos_down`, `no_internet`, `dodo_is_slow`) находились по английским словам из сообщения —
«The internet is down» получало `pos_down=0.50` и `no_internet=0.50` из одних имён файлов.
На русских запросах метрика не изменилась (те же 22 из 25 на наборе), латинские перестали
находить чужое. Заметно это стало только после пункта 5, но задеть могло любого, кто вставит
в чат лог с латиницей.

И ещё: **сводка оператору переехала на шаблон в `config`** (`config.summary.operator` /
`config.summary.subtask`) — формулировки и порядок строк правятся без деплоя. Имя партнёра из
неё убрано: у обращения из веб-виджета автором комментария числится служебный аккаунт Pyrus,
и оператор читал «Партнёр: Pyrus.com».

## Незавершено: смысловой подбор темы

**Зачем.** Подбор по словам сравнивает основы по префиксу: «нужен» не совпадает с «нужно»,
«обновиться» с «обновление». Синонимы автор перечисляет руками. На кластере из семи похожих
статей про кассу — 5 верных из 7. Ломает метрику не число статей (на 22 держалось), а их
похожесть, а большой каталог из похожих и состоит.

**Что сделано.** Каждая статья живёт отдельным исходником в `docs/knowledge/topics/`.
`node tools/build-knowledge.js` собирает из них `docs/knowledge_catalog.json`, документы
`docs/rag/` (имя файла = `key`) и `docs/knowledge-manifest.json` с хешами. Тестовый прогон
проверяет их синхронность и останавливает деплой при ручном рассинхроне. `searchKnowledge`
берёт ключ из `chunk.source.path`, сверяет с каталогом, склеивает фрагменты одной статьи,
отсекает порогом и отдаёт маршрутизатору 2–3 кандидата.

Отказ по порогу теперь настоящий: если RAG доступен и все найденные фрагменты ниже
`minScore`, лексический подбор не возвращает их обратно. Откат на слова остаётся только для
недоступного или действительно пустого RAG.

**Что осталось.** Поставить `rag.mode: "on"` и порог в `config`. Откат мгновенный — вернуть
`mode` в `shadow`.

⚠️ **Прежде чем включать, порог стоит пересмотреть, и вот почему.** `minScore: 1.0` — это
абсолютное число на шкале, которая, по этим же измерениям, **несравнима между запросами**
(2.48 — верное первое место, 2.46 — верное второе, 3.87 — неверное первое). Настроен он на
семи статьях; на тридцати он либо начнёт резать верное, либо пропускать шум, и узнать об
этом можно будет только по жалобам.

Замер из живого чата (10 августа, выгрузка трасс) это подтверждает. Запрос «оборвалось
соединение с сетью, ничего не открывается»: по словам — `no_internet=1.00`, кандидат один;
RAG — `no_internet=2.48, rating_appeal_rejected=2.31, support_complaint=1.69`, отрыв 0.16.
С `minScore: 1.0` маршрутизатор получил бы **три** кандидата вместо одного, причём второй
отстаёт на 0.16. То есть здесь смысловой поиск задачу не облегчил, а усложнил.

Следующий возможный эксперимент — относительный отсев (кандидат проходит, если он не дальше
`k` от лучшего) поверх низкого абсолютного пола. Делать его до набора живых распределений
нельзя: текущие два замера не задают устойчивого `k`. Явный вариант «ни одна не подходит»
у маршрутизатора уже есть.

## Незавершено: чтение Базы Знаний через MCP

**Обновление 2026-08-24.**

**Почему не работало.** Четыре причины, все в коде и графе, ни одна — в MCP-сервере.
`getKnowledgeMcp` вызывала `MCP.call(...)` — такого неймспейса на платформе нет (в
`.agent/system-functions/` его не значится, MCP отдаётся только коллекцией функций для узла
с `type: MCP`). Вся логика лежала внутри `async function main(...)`, которую никто не
вызывал: платформа оборачивает файл сама и отдаёт параметры top-level переменными, то есть
функция не выполняла вообще ничего — отсюда и пустые логи, из-за которых её чинили
добавлением логирования. Узел `function_id_tools_getknowledgemcp_falyc` не имеет
`next-step` и не входит в `tools` ни одного агента, то есть мёртв в графе. И поля ответа
разошлись с реальностью: в результате поиска заголовок называется `articleTitle`, а не
`title`.

**Что измерено на живом сервере.**

- Сервер отвечает **только** `text/event-stream`: с `Accept: application/json` — 406
  «Client must accept both application/json and text/event-stream». Полезная нагрузка в три
  слоя: SSE → конверт JSON-RPC → JSON строкой в `result.content[0].text`. Handshake
  `initialize` не нужен.
- `request.spaces` сервер принимает и честно фильтрует, **но этого поля нет в схеме
  инструмента**, которую экспортировала платформа. Через узел `type: MCP` сузить поиск по
  пространству нельзя — это и решило выбор транспорта в пользу прямого `Http`.
- **Поиск по всей БЗ для маршрутизации непригоден.** «касса» → 50 результатов, первые три —
  новости для кассиров на казахском. «смена превысила 24 часа» → верхнее место верное. Тот
  же класс проблемы, что с порогом RAG выше: FTS работает, когда запрос текстуально близок.
- Статьи из чужих пространств приходят с пустым `content` (проверено, длина 0) или под
  вотермарками — тогда вместо текста служебная заглушка.

**Что сделано.** Транспорт — прямой JSON-RPC поверх `Http` с токеном из `Credentials`
(`kb-mcp-token`, группа `CUSTOM`; читаемость группы `MCP` из кода не проверена, поэтому
ключ MCP-интеграции остался вторым в списке). Поиск сужен нашим пространством
`6d8f5fa3-7fd4-44c8-978d-68743b232533`, происхождение статьи перепроверяется на нашей
стороне, вотермарки и пустое содержимое отсеиваются, каждый отказ называет себя в `error`.
Покрыто `tests/getknowledgemcp.test.js` (22 проверки на подставном `Http`), живой прогон
того же исходника — `node tools/kb-mcp-live.js`.

**Проверено живьём 24 августа**, на новом токене: `node tools/kb-mcp-live.js "смена
превысила 24 часа"` → две статьи из нашего пространства, метаданные разобраны. Побочное
наблюдение, из-за которого в функции появилась одна повторная попытка: один прогон из трёх
получил `socket hang up` на чтении статьи, следующие два прошли целиком. Повтор сделан
только для срывов связи и 5xx — 401 и 400 от повтора не исправятся.

**Формат статьи в БЗ решён и реализован.** Конфигурация статьи лежит в JSON-блоке с той же
схемой, что `docs/knowledge/topics/*.json`, и проверяется тем же линтером — он вынесен из
`tests/run.js` в `tools/lint-topics.js` ровно ради этого.

⚠️ **Грабля, найденная живой записью, а не рассуждением.** Первая версия формата помечала
блок информационной строкой ```` ```json agent ````. База Знаний конвертирует Markdown в свой
внутренний формат, и слово после `json` теряется — статья вернулась с обычным
```` ```json ````, причём с `fidelity: full`. Следствие было хуже самой потери: повторная
публикация не узнавала свою же статью и создала дубль (оба черновика удалены). Признак
переехал внутрь данных — `"schema": "agent-topic/1"`, — и заодно стало лучше исходной идеи:
примеры JSON в тексте статьи больше не могут быть приняты за конфигурацию, а версия формата
теперь есть там, где её можно прочитать.
Проза не дублируется: если уровень в блоке не задан, им становится тело статьи. Статья без
блока — обычная статья БЗ, а не ошибка (в пространстве техподдержки 889 таких). Правила —
`docs/knowledge-tree-format.md`, раздел «Та же статья, живущая в Базе Знаний»; парсер и
обратный рендер — `tools/kb-article.js`, проверки — `tests/kbarticle.test.js`.

Почему не плоские YAML-метаданные, как в первых заметках: ими не выразить уровни `steps` и
`nodes`, то есть в БЗ навсегда остался бы самый слабый уровень статьи. И живой пример, чем
это плохо на практике: статья «CONFIG: Справочник метаданных», которая ОПИСЫВАЕТ разметку
для редакторов, сама содержит пример ```` ```yaml ```` — и возвращалась боту как размеченная
статья с маршрутом `solver`.

**Конвейер БЗ → репозиторий → каталог работает целиком.** `tools/sync-kb.js` тянет наше
пространство, `build-knowledge.js` собирает каталог как раньше. Проверено на переносе
`pos_terminal_troubleshooting`: статья опубликована в БЗ (`08df0280-4425-43e7-86f0-134787c5d592`),
вытянута обратно, и **сгенерированный каталог не изменился ни на байт** — то есть рейс через
БЗ знание не искажает. Единственный дифф в исходнике — форматирование: файл правился руками,
короткие массивы стояли одной строкой. Такое расхождение синхронизация называет
«переформатировано», отдельно от «изменено»: иначе первая же выгрузка показала бы изменения
по всем статьям и настоящая правка утонула бы в шуме.

**Запись ограничена нашим пространством дважды** — заголовком `Mcp-Write-Spaces` и проверкой
в `tools/mcp-client.js` до отправки запроса. Проверено на настоящей статье из «Техподдержка
🛠️»: правка отклоняется у нас, до сети. Серверную половину запрета намеренно не проверяли —
для этого пришлось бы попытаться изменить чужую статью.

**Что осталось.**
1. Проверить на платформе, что `Credentials.get` действительно отдаёт токен из кода. Если
   нет — параметр функции типа `CREDENTIAL`. Локально это не проверяемо в принципе.
2. Прогнать каталог, собранный из БЗ, на платформе: залить `knowledge_catalog`,
   RAG-документы, переиндексировать и пройти живые сценарии. До этого шага «работает»
   означает «работает локально».
3. ✅ Пространство прибрано: шесть статей первых опытов с плоской разметкой удалены,
   справочник для редакторов переписан под блок `schema` и живёт в репозитории
   (`docs/kb-format-reference.md`), в БЗ уезжает командой
   `node tools/kb-publish.js --doc docs/kb-format-reference.md --write`. Осталось две
   статьи: сценарий `pos_terminal_troubleshooting` и этот справочник.
   Примеры в справочнике оформлены фенсед-блоком **без** слова `json` — иначе статья о
   разметке сама опознавалась бы как размеченная. `kb-publish --doc` это проверяет и
   откажется публиковать документ, который выглядит сценарием.
4. `getKnowledgeMcp` по-прежнему не подключён как инструмент агентов: runtime сценариев
   читает каталог из БД. Вместо этого подключена отдельная кодовая функция
   `findOperatorKnowledge` — только на ветке «утверждённая тематика не найдена» и только для
   внутренней подсказки оператору.

## Зачем каталог в БД, если знания в БЗ: замер

Вопрос законный и был задан прямо: если статьи живут в Базе Знаний и читаются через MCP,
зачем собирать `knowledge_catalog`, заливать RAG-документы и держать конвейер. Отвечено
замером, а не рассуждением: `node tools/measure-kb-search.js` прогоняет
`tests/routing.cases.json` — спецификацию «что каталог обязан находить» — через
полнотекстовый поиск БЗ по нашему пространству.

| | Поиск БЗ (FTS) | Подбор по словам (каталог) |
|---|---|---|
| Положительные, 11 запросов | **11 на первом месте, ни одного промаха** | 22 из 25 на прежнем наборе |
| Отрицательные, 9 запросов | молчит 6, **лишнее 3** | явных промахов не измерено |
| Задержка | 145 мс медиана, 271 мс максимум (локально) | чтение документа БД |

**Поиск БЗ — отличный генератор кандидатов и плохой решатель.** Причина трёх ложных
срабатываний важнее их числа: они пришли из фрагмента с **границами** статьи. Запрос
«моноблок не включается» нашёл статью по её же словам «не относится к физической поломке
моноблока»; «интернет не работает во всей пиццерии» — по «общему сбою интернета». FTS не
знает отрицания: слова, которыми статья **исключает** случай, индексируются как
положительный признак. Это структурное свойство, а не плохо написанный текст, и
переписыванием оно не лечится — границы либо есть в статье, либо статья хуже выбирается
моделью.

Отсюда ответ: **каталог в БД — не второй источник правды, а скомпилированный артефакт.** Он
делает две работы, которых у БЗ нет:

1. **Подбор по выверенным полям.** `phrasings` дают запасному подбору только положительные
   примеры; для многословного запроса нужны два слова из одной формулировки. `description`
   читает маршрутизатор, который понимает отрицания. FTS ищет по всему тексту статьи,
   включая её границы.
2. **Обход статьи на каждом витке без сети в критическом пути вебхука.** Дерево читается
   заново каждый виток; через MCP это 1–2 внешних запроса на виток, и срывы связи наблюдались
   (один `socket hang up` из трёх прогонов).

⚠️ **Слабость этого замера, которую надо назвать: в пространстве одна статья бота.** «Первое
место 11 из 11» на одной статье почти ничего не значит — информацию несут только
отрицательные случаи. Решающий замер требует 5–10 размеченных статей, и до него архитектуру
менять нельзя.

**Критерий, при котором рантайм переводится на прямое чтение БЗ** (записан, чтобы не решать
заново): на наборе из ≥5 статей поиск БЗ держит полноту не хуже каталога И даёт не больше
одного лишнего срабатывания на отрицательном наборе. Иначе БЗ остаётся редакторским
источником правды, а рантайм читает снапшот.

**А вот RAG-документы — здесь возражение справедливо.** Это третий механизм для той же
работы: незавершённый, с нерешённой проблемой несравнимого порога (см.
раздел выше). Поиск БЗ на наших данных его уже превзошёл — 11 первых мест против «3.87 у
неверной статьи». Вкладываться в RAG дальше смысла нет: когда придёт время решать по
критерию выше, выбор будет между каталогом и поиском БЗ, а не между тремя механизмами.
После живой ошибки `integrationadapter.rag.not_found` режим по умолчанию изменён на `off`;
`shadow` и `on` остаются только явными экспериментальными настройками.

|---|---|---|
| код, граф, тесты | GitHub, ветка `main` | платформа тянет отсюда сама |

## Незавершено: прозаический уровень статьи и модель под него

**Зачем.** Дерево — самый дорогой способ описать тему, и на большом каталоге оно не
поддерживается: `pos_down` это девять узлов на пять симптомов, а настоящая база по кассам —
десятки моделей на десятки ошибок. Плюс у поддержки уже есть написанные инструкции, и
переписывать каждую в граф с ключами и синонимами — та цена, которая решает, дойдёт ли
каталог до пятидесяти статей.

**Что сделано.** Уровень `article` — статья прозой, разбирается в ней модель. Механически он
существовал и раньше под именем `solverInstruction` и считался наследием; теперь это явный
уровень с именем, валидатором и описанием. Солвер умеет выбрать подходящую партнёру часть,
задать свой различающий вопрос и передать человеку, если статья так говорит. Заодно
починилось: `kind: "handover"` от солвера на линейной статье **не делал ничего** — пустой
текст подменялся отбивкой «мы вернёмся с ответом», и обращение зависало у бота вместо
человека. Условия графа читают `treeEnd`, а его ставила только ветвящаяся статья.

**Что осталось — измерить на настоящей модели.** Симулятор показывает механику, но не
показывает главного: **насколько вероятно, что модель сделает свою работу**, а не вывалит
статью целиком. Это свойство модели, и проверяется только живым прогоном.
`node tests/prose.check.js` печатает три исхода — дерево, проза с работающей моделью, проза с
ленивой — на одних и тех же репликах.

**Модель.** Все четыре агента переключены на созданную в Agent Platform интеграцию
`OPEN_AI - gpt-5.3-chat-latest`; в исходниках узлов сейчас указан её актуальный ключ
`1000299722-open_ai_gpt53chatlat-bvl`. Платформа при импорте меняет ключи интеграций и
переписывает ссылки на них — это штатно, поэтому после каждого деплоя источником актуального
ключа является обратный экспорт платформы. Старый YAML `aliceai-llm-flash` до первого
такого экспорта не удаляется вручную: ресурсами интеграций владеет платформа.

`gpt-5.6-luna` проверена и для этих узлов не подходит: Agent Platform вызывает модель через
Chat Completions и автоматически добавляет `switchToState` как function tool, а провайдер
требует либо Responses API, либо `reasoning_effort: none`. Неизвестное поле настройки
экспортёр удаляет, поэтому исправить это промптом или YAML проекта невозможно. Тест не даёт
случайно вернуть Luna в AI-agent узел до изменения возможностей платформы.

Переключены именно все четыре роли, а не только solver: ближайшие живые тесты должны
одновременно измерить качество сбора юнита, маршрутизации, разбора статьи и подтверждения.
После серии трасс можно будет решить, оправдана ли одна модель везде или узкие
классификаторы стоит вернуть на более дешёвую модель без потери качества.

Отдельный вопрос, который стоит решить до перехода на зарубежного провайдера: **данные
партнёров** (названия точек, ФИО сотрудников, телефоны) в этом случае уходят наружу. Если это
блокирует, реалистичная альтернатива — YandexGPT Pro или GigaChat Max: всё ещё большой шаг от
flash.

## Открытые вопросы и известные ограничения

**Молчание партнёра ничем не обрабатывается.** Чат висит в `awaiting_*` бессрочно: ни
напоминания, ни автозакрытия, ни передачи человеку. Нужен планировщик, а есть ли он на
платформе — не проверено.

**Ответ модели платформа не логирует.** В выгрузке трасс есть только запрос к LLM, поэтому
реплику агента видно лишь в следующем запросе того же блока (роль `assistant`), а последний
его ответ — тот, что уходит в `parseAgentJson`, — не виден вовсе. Судить о нём приходится по
действиям, которые он вызвал. Для отладки промптов это существенно; если у платформы есть
настройка «логировать ответы», её стоит включить.

**Словари «просит человека» и «чистая благодарность» составлены без живых логов.** В
единственном тестовом чате партнёром был автор бота, и ни одной такой реплики там нет.
Механика на месте, дополнять списки нужно по выгрузкам реальных переписок — по одному месту
в `receiveWebhook` на каждый (`ASKS_FOR_HUMAN`, `THANKS_PART`).

**Модель не вызывает инструменты.** Измерено: `matchUnit` — ноль вызовов на семь обращений к
модели в живом чате. Всё, что реализовано ТОЛЬКО в инструменте, надо считать нерабочим, пока
не проверено обратное. `scope: "network"` был именно таким; стоит перечитать остальное с этой
мыслью.

**Тикеты от бота колл-центра** исключены сознательно: у них нет внешнего канала, отвечать
некому. Решение отложено. Опознаются по заполненному полю «Id задачи из КЦ».

**Почтовое цитирование не проверено.** В тестах письма приходили короткими, процитированного
треда в ответах не было. На настоящей переписке подписи и `>`-цитаты могут забить историю
диалога — обрезка по 1200 символов на строку смягчает, но не решает.

**Связь подзадачи больше не зависит от поля формы.** `createSubtask` создаёт нативную
иерархию через `parent_task_id`, подтверждает её по ответу Pyrus и не пишет в поле `95`.
Два одновременных webhook-прогона разводятся атомарным `subtaskClaim`; после неопределённого
HTTP-ответа повтор сначала ищет задачу по `linked_task_ids` и маркеру текущего обращения.

**Чужой бот `bot techSupport Supervisor`** пишет в тикеты на каждый вебхук: «Can't find
settings for Pyrus form with id: 2454249». Это другая интеграция, не наша. Бот его игнорирует
(внутренний комментарий без канала), но тред замусоривается.

**Поля формы тикетов, пока не использованные**, — могут пригодиться как признаки:
`supportbot ON/OFF` (20), `Канал обращения` (27), `Тип обращения` (51).

**Размер фрагмента в базе знаний** меньше самого маленького нашего документа: файл 851 байт
вернулся двумя фрагментами. Пока статей единицы — безобидно; на нескольких десятках стоит
поставить размер фрагмента вручную, больше самого крупного документа.

**`README.md` не отслеживается git** (первая строка `.gitignore`). В свежем клоне его нет.
Существенное продублировано в `docs/`.

## Обновление 5 сентября 2026: semantic retrieval и три последних дефекта

Последние трассы подтвердили три разных класса ошибки, и они исправлены без расширения
словарей и без передачи модели новых полномочий.

- Confirmation правильно понял смысл «да спасибо», но вернул `kind: resolved`. Общий
  parser теперь восстанавливает только точное совпадение `kind === value` при допустимом
  value, актуальном contractId и дословном evidence.
- Routing уже выбрал `ratings_questions` как единственного кандидата, но вернул
  `route: clarify`. Код теперь берёт маршрут такого единственного точного выбора из
  каталога; ноль кандидатов всё ещё означает handover, два — один различающий вопрос.
- Operator Assist получил пустой список статей и придумал «систему управления курьерами».
  Добавлен отдельный `Knowledge Query Planner` с максимум двумя вариантами; MCP ищет
  support-first и читает отобранную статью. Без статьи черновик принудительно null.

Read-only запросы к живому MCP показали, что статья о личной карточке сотрудника находится
по исходному запросу лишь на 14-й позиции, а по смысловым вариантам — на первой. Сервер
запрещает полное чтение (`canReadFully: false`), но `search_in_content` возвращает нужный
фрагмент: роль Менеджера офиса, «Команда → Сотрудники», личную карточку и фото 300×300.
Кодовый срез `3a0d9b0`, локальная регрессия `1257/1257`.

## Потолок сегодняшней архитектуры

Отдельная оценка, чтобы не переоткрывать её заново. Сейчас бот способен на «любую тему,
которую можно решить разговором, **если её удалось найти**». Четыре ограничения, по убыванию
важности:

1. **Найти статью.** Именно этим занят незавершённый пункт выше.
2. **Бот умеет только спрашивать, но не узнавать.** Источники фактов — партнёр и каталог.
   Инструментов чтения внутренних систем нет ни одного, поэтому темы вида «проверьте, прошла
   ли оплата» не выразимы.
3. **Бот умеет только говорить, но не делать.** Действий пять: сказать, спросить, закрыть,
   создать подзадачу, отдать человеку.
4. **Ветвление только по словам партнёра.** Условий по данным задачи («если юнит в Москве»,
   «если это кофейня») в формате нет.

Порядок важен: без п.1 остальные не окупятся, потому что до правильной статьи не доходит.

## Грабли, на которые уже наступали

Коротко, чтобы не наступить снова. Подробности — в комментариях кода, там же и история.

- **Экспорт платформы удаляет `docs/`, `tests/`, `tools/`.** Каждый деплой. См. `deploy.md`.
- **Точечная запись в БД**: фильтр по `taskId` (не по ключу документа), пути без префикса
  `value.`, массив в значении `$set` платформа не принимает — на любой глубине. В одном
  `$set` нельзя одновременно писать родительский и дочерний путь (`data` вместе с
  `data.handoverReason`): MongoDB отклоняет всю операцию с code 40.
- **`Http` не отдаёт тело ответа при не-2xx.** Причину 400 из Pyrus в логе не увидеть,
  поэтому диагностику пишем сами.
- **Синтаксис Node.js шире синтаксиса Agent Platform.** Unicode property escapes в
  регулярных выражениях проходят локальную компиляцию, но платформа отклоняет всю функцию.
  `tests/run.js` теперь проверяет этот известный разрыв отдельно; для русского и английского
  текста используются явные диапазоны символов.
- **Номера полей у копии формы другие.** Поля ищутся по имени, номер в `config` — аварийный
  выход.
- **В этой организации Pyrus у каждого бота email вида `bot@<uuid>`** — опознавать своих
  можно только по id из `config.botAuthorIds`.
- **Ответ без `channel` уходит во внутреннюю переписку, а Pyrus отвечает 200.** Партнёр
  ничего не получает. Бот теперь в такой ситуации передаёт обращение оператору.
- **Слова, называющие КТО пишет** («пиццерия», «Додо»), в документах базы знаний превращают
  статью в магнит для чужих запросов. `build-knowledge.js` их перечисляет.
- **Идентификатор, попавший в поиск, находит сам себя.** Ключи статей латиницей находились по
  английским словам из сообщения партнёра. Ключ — для кода, лексический текст для
  сравнения — только `phrasings`; `description` читает модель и смысловой индекс.
- **Реализовать что-то только в инструменте — значит не реализовать.** Модель инструменты
  вызывает редко (измерено: ноль из одного уместного случая), а запасной путь в коде про
  задумку инструмента не знает.
- **Автор комментария в Pyrus — не обязательно человек.** У обращения из веб-виджета автором
  числится служебный аккаунт `Pyrus.com`, и он приезжал оператору как имя партнёра.
