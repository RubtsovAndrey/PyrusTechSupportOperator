# Точки воздействия на бота

Где что менять, чтобы бот повёл себя иначе. Каждый раздел отвечает на один вопрос:
**что именно правится, где это лежит и чем за это платят.**

Три вещи стоит знать до первой правки, потому что они объясняют, почему поведение
лежит не там, где его ищут:

- **Свободный текст партнёру формулирует только `agent_response_composer`.** Он получает
  уже разрешённый `responsePlan`; решение и факты до него выбирают policy, MCP и Solver.
  Приветствие, ссылки, контрольный вопрос и стандартные ответы собирает `applyOutcome`.
- **Ход диалога решает не модель, а статья БЗ.** Какой вопрос задать, куда пойти после
  ответа, чем закончить — это `knowledge_catalog`. Модель только распознаёт, что сказал
  партнёр, и пересказывает готовую инструкцию.
- **Факт, который можно вычислить кодом, от модели не зависит.** Юнит пишет `matchUnit`,
  конечные и открытые ответы проверяют `parseTurnInterpretation`/`parseOpenAnswers` вместе
  с `searchKnowledge`, приветствие формирует `applyOutcome`.
  Промптом такие вещи не исправляются: там их просто нет.

## 1. Промпты агентов

Девять файлов, по одному на agent-узел. Промпт — это три поля `system-promts`: `role`, `goal`,
`instructions`, плюс `query-override` (что агенту велено сделать с текущим сообщением).

| Файл | Кто это | Инструмент | Что решает |
|---|---|---|---|
| `nodes/agents/agent_intake.yml` | приём обращения | `matchUnit` | эскалация по просьбе/агрессии, юнит, суть проблемы |
| `nodes/agents/agent_routing.yml` | маршрутизатор | `searchKnowledge` | какая тематика из каталога |
| `nodes/agents/agent_turn_interpreter.yml` | смысл текущей реплики | — | одно конечное value общего контракта: ответ статьи, confirmation или post-close intent |
| `nodes/agents/agent_open_answer_interpreter.yml` | открытые ответы статьи | — | только объявленные свободные ключи, дословное evidence и возможное противоречие |
| `nodes/agents/agent_solver.yml` | внутренний читатель policy | `searchKnowledge` | разрешённый `contentPlan`, вопросы статьи, совместимые старые ветки |
| `nodes/agents/agent_response_composer.yml` | внешний голос | — | формулировка уже разрешённого `responsePlan`, без выбора решения |
| `nodes/agents/agent_operator_assist.yml` | черновик оператору | — | одно неотправленное первое сообщение по переписке и отфильтрованным excerpt |
| `nodes/agents/agent_summary_subtask.yml` | внутренняя сводка | — | кратко пересказывает переписку для подзадачи |
| `nodes/agents/agent_summary_handover.yml` | внутренняя сводка | — | кратко пересказывает переписку для оператора |

**Разделение агентов жёсткое:** у intake нет доступа к БЗ, у solver — к каталогу юнитов;
оба Interpreter, Composer и Operator Assist не имеют инструментов. Interpreter не отвечает
партнёру, Composer не читает policy и не выбирает действие, Operator Assist пишет только во
внутреннюю заметку. Менять границы следует только вместе с входным/выходным контрактом и
отдельным eval.

### Что здесь менять можно

- **Формулировки правил и запретов.** Почти весь intake-промпт — это список того, чего
  спрашивать нельзя (`ЗАПРЕЩЕНО СПРАШИВАТЬ`), и он написан по следам живых прогонов.
  Новый лишний вопрос от бота лечится строкой в этом списке.
- **Настройки модели** (`llm-model-settings`): `temperature`, `max-tokens`. Произвольные
  параметры API сюда добавлять нельзя: экспортёр удаляет неизвестные поля. В частности,
  `gpt-5.6-luna` пока несовместима с AI-agent узлами — Chat Completions отвергает их
  системный function tool, а `reasoning_effort: none` платформа передать не умеет.
- **Лимиты вызовов инструментов**: `sequential-tool-calls-limit`, `unique-tools-count-limit`.
  У Turn Interpreter и Response Composer `tools: []`. Solver сохраняет инструменты для
  чтения статьи, внешней allowlist-БЗ и совместимых старых веток; защищённый ответ больше
  не зависит от его повторного tool-вызова.

Маршрутизатор обязан дочитать разговор и уточнить один различающий признак, если тема ещё
неясна. После уверенного выбора `topicKey` закрепляется до конца непрерывного чата: поздняя
реплика уточняет текущую проблему, но не запускает новую маршрутизацию. После закрытия
общий post-close контракт отделяет чистую благодарность; всё остальное отдаётся оператору.

### Что менять нельзя, не меняя код

- **Формат JSON в последней строке `instructions`.** Его разбирает `parseAgentJson`, и
  имена полей там жёсткие: `action`, `clarifyKind`, `unitFullName`, `scope`,
  `problemSummary`, `email` у intake; `topicKey`, `route`, `componentName` у routing;
  `contentPlan`, `kind`, `responseMode`, `answers` у solver; `caseSummary` у двух
  summary-агентов. `parseTurnInterpretation` ждёт `kind`, `contractId`, `value`,
  `evidenceText`; `parseResponseComposition` — `planId`, `replyText`, `partnerLanguage`.
  Переименование требует одновременного изменения parser и тестов.
- **Список `clarifyKind`.** Значения из этого списка ищет `UNIT_QUESTION` в `applyOutcome`;
  неизвестное значение даст вопрос по умолчанию.
- **`scope: "network"` у intake.** По этому слову `parseAgentJson` подставляет первую точку
  сети, когда партнёр пишет от лица сети целиком и номера точки не существует. Раньше это
  умел только инструмент `matchUnit`, а выгрузка живого чата показала, что flash-модель
  инструмент не вызывает вовсе — то есть вся ветка работала только в теории, а на практике
  партнёра трижды спрашивали номер, которого нет.
- **Список `value` контракта confirmation.** Значение `question` среди них — не роскошь:
  без него «а где эту крышку искать?» приходило как `unclear` и обращение уходило человеку
  без ответа. Сами значения задаются в `receiveWebhook`, а не в промпте агента.
- **Приветствие и прощание.** В промптах стоит запрет здороваться, и он нужен:
  приветствие добавляет `applyOutcome` по факту наличия ответов бота в треде.
  Разрешите здороваться модели — бот поздоровается дважды.

### Язык разговора

Всем ролям, работающим с внешним разговором, велено учитывать **язык партнёра**. Раньше
«пишет не на русском» стояло в промпте intake рядом с агрессией, то есть язык считался
неисправностью. Summary-агенты пишут по-русски для оператора, а Turn Interpreter вообще
не формирует внешний текст.

Понимать при этом надо ограничение, и оно существенное: **на язык партнёра переходит только
то, что говорит модель.** Всё, что собирает КОД, по-прежнему русское — уточняющий вопрос,
приветствие, отбивки `OUTCOMES.defaultReply`, «Получилось решить вопрос?». То есть разговор
на другом языке получается наполовину русским. Плюс сам подбор статьи ищет по русским
словам (`description`, `phrasings`) и по русской базе знаний, так что обращение на другом
языке скорее не найдёт статью и уйдёт человеку — это правильная деградация, но деградация.

Задел на будущее оставлен: `receiveWebhook` определяет **письменность** последнего сообщения
и пишет её в `runtime.lang` (`cyrillic` / `latin` / `null`, если сообщение слишком короткое).
Различается письменность, а не язык: отличить украинский от русского кодом нельзя, а язык
понимает модель, читая само сообщение. По этому полю видно, сколько таких обращений вообще
бывает и стоит ли переводить фразы кода; оно же будет выбирать язык, когда переводы появятся
(тогда — таблицей рядом с шаблонами сводки, там же, в `config`).
- **`structured-output-enabled`** включать бессмысленно как гарантию: у YandexGPT это
  системная инструкция, а не грамматика. `parseAgentJson` остаётся предохранителем в
  любом случае.

## 2. Что модель видит кроме промпта

Половина поведения задаётся не промптом, а **заметками**: платформа сериализует
`AgentContext` в системное сообщение, и модель читает их наравне с инструкциями.
Заметка с готовым ответом надёжнее правила «посчитай сам» — маленькая модель считает плохо.

| Заметка | Где собирается | Что в ней |
|---|---|---|
| История диалога | `receiveWebhook/code.js` (`HISTORY_LIMIT`) | реплики с ролями: Партнёр / Ассистент / Оператор |
| «Известные данные по обращению» | `receiveWebhook/code.js`, сборка массива `lines` перед `addNote` | юнит, проблема, email, тематика, число выданных решений, **«Не хватает для продолжения»**, а также **«Уже собрано по тематике»** и **«Ещё не отвечено»** — они нужны прямому возврату на стадию статьи; для защищённого вопроса рядом добавляется отдельный конечный контракт Interpreter |
| «Текущее сообщение партнёра» | `receiveWebhook/code.js`, заметка «Текущее сообщение партнёра» | на что отвечать |
| «Уточнённые данные по обращению» | `parseAgentJson/code.js`, сборка `lines` в конце функции | то же после разбора витка + **«Уже собрано по тематике»** и **«Ещё не отвечено (ключ — вопрос)»** |

Две строки здесь несут больше, чем весь остальной промпт:

- **«Не хватает для продолжения»** — единственное, на что intake разрешено опираться,
  решая «спросить или ехать дальше». Список считает код; модель его не пересчитывает.
- **«Ещё не отвечено»** — перечень ключей статьи с вопросами, к которым они относятся.
  Именно она позволяет solver вытащить из первого сообщения партнёра то, что статья
  собиралась спрашивать, и не спрашивать этого вовсе.

**Что в заметки не попадает намеренно:** токен Pyrus и `api_url` (секреты), журнал
`attempts`, узлы дерева (`treeNode`, `treeEnd`, …). Внутренности статьи в промпте только
провоцируют модель рассуждать о них вместо ответа партнёру.

## 3. Правила ответа в коде

Всё в `functions/ID_Actions/applyOutcome/code.js`.

### Таблица исходов `OUTCOMES` (`const OUTCOMES` в `applyOutcome`)

Вся машина состояний — одна таблица. Новый сценарий = строка здесь плюс узел в графе.

| Исход | Стадия после | Что делает в Pyrus | Текст по умолчанию |
|---|---|---|---|
| `clarify` | `gathering` | — | «Уточните, пожалуйста, детали вопроса.» |
| `clarify_email` | `awaiting_email` | — | просьба назвать email |
| `clarify_answers` | `awaiting_answers` | — | «Уточните, пожалуйста, детали вопроса.» |
| `reply` | `awaiting_confirmation` | — | «Понадобится время…» |
| `solved` | `closed` | `action: finished` + 2 поля | «Рад был помочь!…» |
| `escalated` | `escalated` | `approval_choice: approved` + поля | «Понадобится время…» |
| `subtask_created` | `closed` | `action: finished` + 2 поля | «Обращение создано и передано специалистам…» |
| `handover_silent` | `escalated` | `approved` + поля | ничего, партнёру не пишем |

`defaultReply` — это то, что услышит партнёр, если модель ничего не сказала. Правится здесь.

Три исхода ждут ответа партнёра (`ASKING`) и потому считаются ограничителями
зацикливания. Разница между ними одна — куда вернётся ответ: `clarify` в intake,
`clarify_email` сразу в `createSubtask`, `clarify_answers` в Turn Interpreter при полном
конечном контракте вопроса либо в совместимый `agent_solver`. Заводя
новый исход, который о чём-то спрашивает, добавьте его в `ASKING`: иначе он окажется
единственным путём в графе, на который лимиты не действуют.

Столбец «поля» — это `withFieldUpdates`. Сам массив `field_updates` собирает `finalize` из
`data.unitFullName`/`data.componentName` и id полей в `runtime`; в `pendingOutcome` его нет
намеренно — массив внутри значения `$set` платформа не принимает.

**Закрытие имеет жёсткий контракт:** юнит и компонент уже определены, а в webhook найдены
id обоих полей формы. Только тогда `finalize` одним комментарием отправляет
`action: finished` и ровно два `field_updates`. `approval_choice` при закрытии запрещён:
он передаёт чат на следующий этап, автоматизация которого снова открывает задачу. Если
отсутствует хотя бы одно условие,
`action: finished` не отправляется: исход превращается в утверждённую передачу оператору,
а во внутренней переписке перечисляется, чего не хватило. Если партнёр уже подтвердил
решение, он всё равно получает финальное «Рад был помочь»: передача нужна только для
классификации, поэтому шаблон «требуется время на изучение» здесь неверен. Эта проверка стоит и при выборе
исхода, и непосредственно перед HTTP-запросом, поэтому защищает также незавершённые
документы от предыдущей версии кода.

### Уточняющий вопрос (`UNIT_QUESTION` … `if (isClarify` в `applyOutcome`)

Вопрос **не выбирается моделью, а собирается из того, чего не хватает в документе задачи**,
и покрывает всё недостающее сразу. Это не стиль, а лечение живого дефекта: пока вопрос
выбирала модель, она спрашивала юнит, потом проблему, потом снова юнит — по одному факту
за виток, бесконечно. Вопрос, который спрашивает про всё, зацикливаться не может: он
сжимается с каждым ответом, а когда сжиматься некуда — спрашивать нечего.

- `UNIT_QUESTION` — формулировка про точку под каждый `clarifyKind`;
- `UNIT_QUESTION_DEFAULT` — когда `clarifyKind` не подошёл;
- `PROBLEM_QUESTION` — формулировка про суть проблемы;
- склейка: `"Подскажите, " + части.join(", а также ") + "?"`.

Вопросы solver сюда не попадают: их текст несёт вопрос статьи, и его нельзя подменять.

### Приветствие (`const GREETED` в `applyOutcome`)

Решается по треду Pyrus (`runtime.isFirstBotReply`), а не моделью, которая ошибалась в
обе стороны. В первом ответе приветствие добавляется, если модель не поздоровалась сама;
в последующих — срезается регуляркой. Список слов приветствия — там же.

### Когда бот сдаётся (`MAX_CLARIFY_STREAK` / `MAX_TREE_QUESTIONS` в `applyOutcome`)

| Предел | Где | Значение | Смысл |
|---|---|---|---|
| `MAX_CLARIFY_STREAK` | `applyOutcome` | 3 | столько **бесплодных** вопросов подряд — и чат уходит человеку |
| `MAX_TREE_QUESTIONS` | `applyOutcome` | 12 | столько вопросов на статью; глубже — ошибка в статье, а не диалог |
| `MAX_IGNORED` | `searchKnowledge` + `parseAgentJson` | 2 | столько реплик подряд после доставленного вопроса, не ответивших на него |
| `MAX_EXPLANATIONS` | `nextSolutionStep` | 2 | столько раз можно разъяснить один и тот же совет |

Считается **прогресс, а не вопросы**: виток, сменивший узел статьи, обнуляет серию.
Иначе дерево, которое законно спрашивает три вещи по делу, отдавали оператору за один
вопрос до подзадачи, которую оно собиралось создать.

Два последних предела появились потому, что общего счётчика для них не хватает, и это
стоит понимать, прежде чем их сводить в один. `MAX_IGNORED` считает только вопрос, который
`finalize` действительно доставил в Pyrus. На границе `searchKnowledge` ещё не передаёт
чат: `parseAgentJson` сначала читает итоговый `answers` текущего solver-вызова. Только если
ответа всё ещё нет, оператор видит честную причину «система не смогла извлечь ответ из
двух реплик партнёра», а не обвинение партнёра и не «бот задал 3 уточняющих вопроса».
`MAX_EXPLANATIONS` вообще
нельзя считать общим счётчиком: разъяснение выходит исходом `reply`, как и обычный совет,
так что общий предел превратил бы три совета подряд в передачу человеку.

### 3.1. Что бот слышит кодом на любой стадии

Три вещи проверяются в `receiveWebhook` до общего диалогового потока — то есть
работают и на вопросах статьи, и на ожидании email, и на подтверждении. Модели это не
стоит ни одного вызова, кроме смыслового fallback для незнакомого post-close текста.

| Признак | Список | Стадия | Что дальше |
|---|---|---|---|
| Просьба человека | `ASKS_FOR_HUMAN` | любая рабочая | `handover_request` → сводка оператору, причина «партнёр попросил связать его с человеком» |
| Чистая благодарность | `THANKS_PART`, затем общий контракт `post_close` | только `closed` | точный fast path или `gratitude_only` → «Рад был помочь»; `other/unclear` → тихая передача |
| Просьба закрыть чат | `CLOSE_REQUEST` | любая рабочая | `close_request` → «Понял, обращение закрываю», чат закрывается без передачи |

Список просьб человека заведомо неполон и пополняется только по живым логам. Словарь
благодарностей теперь не должен расти вслед за каждой разговорной формой: он остаётся
дешёвым высокоточным fast path, а незнакомая формулировка проверяется Turn Interpreter по
двум значениям `gratitude_only|other` с доказательством, равным всему сообщению.

Про просьбу человека важно одно правило, и оно объясняет, почему список выглядит громоздко:
**голое существительное брать нельзя**. «Переведите сотрудника в другую пиццерию» — законная
ветка статьи про карточку, «менеджер офиса меняет аватарку сам» — цитата из самой базы
знаний, «оператор кассы сказал» — рассказ о проблеме. Поэтому ищется просьба: повелительный
глагол рядом со словом о человеке, либо прямо названное «живой человек» / «не бот».
В выбранном рейтинговом сценарии узкая фраза «передайте специалисту» продолжает сбор для
профильной подзадачи на стадиях подтверждения, вопросов статьи и email. «Позовите живого
оператора» этим исключением не покрывается и немедленно отдаёт сам чат человеку.

Про благодарность — цена ошибок несимметрична, и оба слоя подстроены под это. Быстрый слой
принимает только сообщение, где благодарность — **каждая** часть. Смысловой слой обязан
процитировать всё текущее сообщение, поэтому не может выбрать одно слово «спасибо» и
проигнорировать вопрос рядом. «Да, получилось, спасибо» подходит, «Спасибо, а теперь
другое дело» — нет; невалидный или неоднозначный frame считается `other` по последствиям.
**Защита переоткрытых чатов при этом не снимается**: всё, кроме чистой благодарности,
по-прежнему уходит человеку — иначе в одной задаче окажутся два разных обращения, в которых
бот путается.

Про закрытие действует такой же осторожный принцип: одновременно требуются действие и
объект текущего разговора (`чат`, `обращение`, `заявка`, `задача`, `тикет`). Поэтому
«закройте крышку кассы» и «нужно закрыть смену» не завершают чат, а явное отрицание вроде
«не закрывайте чат» исключает срабатывание. Если в одной реплике партнёр всё же просит и
закрыть чат, и позвать человека, просьба человека имеет приоритет.

|---|---|---|
| «Получилось решить вопрос?» — вопрос после совета по умолчанию | `searchKnowledge/code.js`, `DEFAULT_FOLLOW_UP` | `DEFAULT_FOLLOW_UP`, перекрывается `followUpQuestion` статьи |

## 4. База знаний: как получить нужный результат

На платформе статьи читаются из документа БД `knowledge_catalog`, но редактируются в
репозитории по одной в `docs/knowledge/topics/`. `node tools/build-knowledge.js` собирает из
них `docs/knowledge_catalog.json`; именно этот сгенерированный файл загружается в БД.
Полный формат — в `docs/knowledge-tree-format.md`. Здесь — только правила «хочу такое
поведение → пишу так».

**Прежде всего выберите уровень статьи.** Их четыре — `route`, `article`, `steps`, `nodes`, —
и правило одно: берите самый дешёвый, который даёт нужный результат. Таблица и признак выбора
— в начале `knowledge-tree-format.md`. Дерево нужно там, где обязательно собрать поля или
взять компонент из ветки; всё остальное дешевле и живее написать прозой.

### 4.1. Как статья попадает в выдачу

Запасной поиск по словам использует утверждённые `phrasings`. Считаются **только те слова
запроса, которые каталог знает хотя бы в одной формулировке**; имя сотрудника, город и
номера в счёте не участвуют. Для многословного запроса минимум два разных словесных корня
должны совпасть в одной и той же формулировке. Повтор одного корня в разных формах
(`печатает` / `печать`) остаётся одним признаком; одного общего признака недостаточно.

`description` читает маршрутизатор и смысловой индекс, но не запасной подбор. В нём можно
явно описывать границы («не относится к общему сбою интернета»), не превращая слова
исключения в положительный сигнал.

⚠️ **`key` в подборе не участвует.** Он идентификатор для кода, и как текст он вредил:
ключи латиницей (`pos_down`, `no_internet`, `dodo_is_slow`) находились по английским словам
из сообщения — запрос «The internet is down» получал `pos_down=0.50` и `no_internet=0.50` из
одних имён, и партнёр уезжал в статью про кассу. То же ждало любого, кто вставит в чат лог
с латиницей. Иначе метрика работала бы наоборот: чем подробнее партнёр описал
проблему, тем ниже оценка статьи про неё (так и было, и чат уходил оператору со нужной
статьёй в каталоге).

- **В `description` кратко объясняйте предмет и границы темы** языком, понятным
  маршрутизатору. Внутренние классификаторы вроде «инцидент класса P2» без пояснения не
  помогают.
- **В `phrasings` пишите отдельные реальные формулировки партнёров.** Не общий список слов,
  а короткие фразы, каждая из которых сама достаточно специфична для этой темы.
- **Не пишите в `description` того, чего в теме нет.** Оценка делится на число известных
  каталогу слов запроса, и лишние слова растаскивают темы друг у друга.
- Ничего не нашлось — возвращается `found:false` без кандидатов, и обращение уходит
  человеку. Сырые RAG-фрагменты модели не показываются: иначе она может угадать тему,
  которую порог только что отверг. Лог при этом сохраняет кандидатов и оценки — это готовый
  ответ на «почему не нашло» без влияния диагностики на решение.

### 4.2. Хочу, чтобы бот…

| …повёл себя так | Пишу в статье |
|---|---|
| Дал ответ и закрыл чат — партнёр решит сам | узел с `advice` и `end: "close"` |
| Собрал данные и создал подзадачу | узел(ы) с `ask`, ветка кончается `end: "subtask"`, у темы или ветки есть `componentName` |
| Помогал по шагам и ждал результата | линейная статья: `steps` по одному совету, `followUpQuestion`, `onFail` |
| Собрал данные и передал человеку | `ask` + `end: "escalate"`, при нужде `askBeforeHandover` |
| Сразу отдал человеку, без вопросов | тема без `nodes` и `steps`, `route: "escalate"` |
| Задал разные вопросы в разных случаях | `branches` с `when`/`go` от узла-развилки |
| Не спрашивал того, что партнёр уже сказал | у вопроса есть `key`; ответ читается из переписки и из `when` |
| Показал первой линии человеческие названия полей | у каждого `ask` есть `label` |

### 4.3. Правила, которые экономят витки диалога

- **Ключ у вопроса — это право ответа быть сохранённым.** Есть `key` — ответ пишется в
  задачу, попадает в сводку и второй раз не спрашивается. Нет ключа (вопрос строкой в
  линейной статье) — ответ живёт один виток и до человека не доедет.
- **`label` — как поле называется для человека.** Без него в подзадаче печатается сам
  ключ, и первая линия читает «newValue: +79001234567». Один ключ в разных ветках может
  иметь разные подписи; побеждает подпись того узла, на котором диалог закончился.
- **Один узел — один смысл.** Если узел и спрашивает данные, и ветвится, укажите
  `branchOn` — какой из его вопросов читают ветки. Иначе ответ «Иванов Иван» будет
  сопоставляться с вариантами развилки.
- **`when` — это синонимы ответа, а не текст для партнёра.** Варианты партнёру не
  перечисляются; по ним код узнаёт его слова, в том числе сказанные в первом сообщении.
- **Не задавайте вопросов «на всякий случай».** Каждый вопрос — виток и риск потерять
  партнёра. Спрашивайте то, без чего первая линия не сможет работать.
- **Дерево всегда входит через solver,** что бы ни стояло в `route`: маршрут решает
  ветка, в которую пришёл партнёр, а прыжок сразу в подзадачу пропустил бы все вопросы,
  ради которых дерево и написано.

### 4.4. Чем проверить статью до заливки

`node tests/catalog.check.js` прогоняет сгенерированный `docs/knowledge_catalog.json` настоящим кодом
`searchKnowledge` по всем сценариям и печатает: нашлась ли тема и с какой оценкой,
сколько витков, какие вопросы, чем кончилось, **и итоговые тексты оператору и в подзадачу**.
Это самый быстрый способ увидеть свою статью глазами первой линии, не деплоя ничего.

### 4.5. Общая БЗ при неизвестной теме

Если маршрутизатор не нашёл утверждённую тему, `cond_routing_subtask` направляет виток в
`func_find_operator_knowledge`. Функция `ID_Tools/findOperatorKnowledge` ищет по всей БЗ,
доступной токену, и возвращает не больше трёх опубликованных статей. `applyOutcome` добавляет
их только во внутреннее саммари.

Где менять:

| Что | Место |
|---|---|
| число подсказок | `findOperatorKnowledge/code.js`, `LIMIT` |
| длина фрагмента | там же, `EXCERPT_LIMIT` |
| фильтры published / watermarks / релевантность / дубликаты | там же, `relevance`, `spacePriority` и цикл по `hits` |
| вид блока во внутренней переписке | `applyOutcome/code.js`, `operatorKnowledgeBlock` |
| точка запуска в графе | `nodes/conditions/cond_routing_subtask.yml` |

Не подключайте эту функцию инструментом маршрутизатора: поиск не должен превращать
ближайшую статью в решение. Ошибка или пустой результат MCP обязаны оставить обычный
handover рабочим.

`search_content` не возвращает score и может найти сотни статей по одному общему слову.
Поэтому порядок MCP не считается готовой выдачей: кандидаты фильтруются по значимым словам,
затем ранжируются как «наше пространство → пространства техподдержки → остальная БЗ».
Совпадающие заголовки схлопываются. Ослаблять этот фильтр следует только по живым трассам:
для операторской подсказки пропуск полезной ссылки дешевле, чем три уверенно выглядящих,
но случайных материала.

## 5. Итоговые сообщения: оператору и в подзадачу

### Правится в `config`, без деплоя

Текст лежит **шаблоном**, и шаблон перекрывается документом `config`:

```json
{
  "summary": {
    "operator": "[Внутренняя переписка]\nБот передаёт обращение оператору.\n\nЮнит: {unit}\nЯзык: {language}\nДомен юнита: {unitDomain}\nEmail: {email}\nТематика: {topic}\nСуть: {problem}\nПричина передачи: {reason}",
    "subtask": "Обращение передано ботом техподдержки.\n\nСуть: {problem}"
  }
}
```

Так меняются формулировки, порядок строк и то, какие строки вообще печатать — а раньше за
каждую запятую платили деплоем, причём правкой в двух файлах сразу. Значения по умолчанию —
`const SUMMARY` в коде; пустая или отсутствующая строка в `config` означает «взять
встроенную».

| Плейсхолдер | Что в нём |
|---|---|
| `{unit}` | юнит из каталога или «не определён» |
| `{email}` | email партнёра или «не указан» |
| `{language}` | язык партнёра или рабочее предположение о русском |
| `{unitDomain}` | домен юнита или рабочее предположение о РФ |
| `{topic}` | ключ статьи + описание (обрезано до 70 символов) или «не определена — подходящей статьи в базе нет» |
| `{problem}` | сводка фактов из сообщений партнёра с учётом контекста диалога; при сбое summary-агента — краткая суть из intake |
| `{collected}` | устаревший совместимый плейсхолдер; всегда пуст, чтобы старый `config` не печатал фрагменты |
| `{tried}` | устаревший совместимый плейсхолдер; всегда пуст |
| `{reason}` | причина передачи человеку |
| `{component}` | компонент подзадачи |
| `{parent}` | номер исходной задачи |

Неизвестный плейсхолдер **остаётся в тексте как есть**: опечатку в `config` лучше увидеть в
сводке, чем молча получить пустое место.

Функции платформы не импортируют друг друга, поэтому блок шаблона существует в двух копиях
(`applyOutcome` и `createSubtask`) — но следит за ними уже не человек: `tests/run.js`
проверяет, что копии посимвольно совпадают, тем же способом, каким сторожит восемь копий
`writeState`. Подписи полей берёт `topicForm` (тоже в двух копиях, рядом).

### Одна форма на оба случая

Читает их один человек, поэтому смысловой центр один: **цельная краткая сводка всего
разговора**. Служебные поля добавляются только во внутреннюю передачу оператору.

```
[Внутренняя переписка]
Бот передаёт обращение оператору.

Юнит: [drinkit.ru] Москва 0-22 (Дмитровское шоссе, 163А)
Email: manager@example.ru
Тематика: employee_card_change — изменить данные сотрудника в карточке…
Суть: Партнёр хочет исправить номер телефона сотрудника. Уточнил сотрудника, новый номер
и причину изменения. Ответ из Базы знаний не решил вопрос, поэтому партнёр попросил
передать обращение специалисту.

Причина передачи: не указана
```

Различается обрамление сводки:

| | Внутренняя переписка | Подзадача |
|---|---|---|
| Заголовок | `[Внутренняя переписка]` + «Бот передаёт обращение оператору.» | «Обращение передано ботом техподдержки.» |
| Остальное | юнит, язык, домен, email, тематика и причина передачи | только «Суть»; юнит, email, компонент и родительская связь находятся в полях Pyrus |

**Имени партнёра в сводке нет намеренно.** Оно бралось из автора комментария, и для почты
работало; для веб-виджета автором числится служебный аккаунт Pyrus, и оператор читал
«Партнёр: Pyrus.com» — похоже на название организации-контрагента (видно в выгрузке живого
чата). Настоящего имени у веб-виджета нет вовсе — `Anonymous user`, — а отвечают партнёру по
каналу задачи, а не по имени.

### Что печатается всегда, а что при наличии

- **Всегда, даже пустым:** юнит, email, тематика, суть обращения. Пустота здесь
  тоже факт: «Email: не указан» говорит, что спросить его не удалось. Если проблема ещё
  не описана, сводка прямо сообщает об этом; если проблема известна, но подготовленная
  тема не найдена, это указывается отдельно. У найденной темы при необходимости остаётся
  пометка «статья предписывает передать обращение человеку».
- **Отдельные ответы статьи не печатаются:** семантические значения и точные реплики
  сохраняются для маршрутизации и диагностики, но обрывки делают итог труднее читать.
- **Текст рекомендации не дублируется:** полная переписка доступна в родительском чате,
  а summary-агент отражает в «Сути» только значимый результат общения. Факты он берёт
  только из сообщений партнёра; сообщения бота служат контекстом, но не источником.

### Куда эти тексты попадают в Pyrus

- **Оператору** — комментарием **без `channel`**, то есть во внутреннюю переписку;
  партнёр его не видит. Отправляет `finalize`, до реплики партнёру. Пишется перед каждой
  передачей, включая молчаливую (переоткрытый чат) и срыв по лимиту вопросов.
- **В подзадачу** — в поля формы «Входные данные»: `subjectFieldId` → «Тема» (суть
  обращения), `messageFieldId` → «Сообщение» (весь текст). Прямо в теле создания, одним
  запросом. «Сообщение» обязательно: если поле не найдено или Pyrus его не принимает,
  подзадача не считается успешно оформленной, исходный чат не закрывается и передаётся
  оператору. Повтор без «Темы» допустим, без «Сообщения» — нет.

## 6. Конфигурация и каталоги

Документы БД, правятся вручную и действуют сразу.

| Документ | Что внутри |
|---|---|
| `knowledge_catalog` | статьи, см. раздел 4 |
| `config.summary` | шаблоны сводки оператору и в подзадачу, см. раздел 5 |
| `unitCatalog` | массив строк FullName из Pyrus как есть: `["[dodopizza.1]Москва 1-1 (ул. Ленина 1)", …]`. Бот сам вынимает бизнес из `[...]` и имя до скобок; техническое значение «Не нужно» отбрасывает. Нечёткий поиск по длинной реплике требует не менее двух совпавших идентифицирующих частей. Обновляется вручную, раз в неделю |
| `config` | где боту работать (`forms`), id сервисного аккаунта (`botAuthorId`), форма подзадачи и её поля |

`config` перекрывает значения по умолчанию из `createSubtask/code.js`, `const DEFAULTS`:
`subtaskFormId: 2454249` (тестовая целевая форма подзадач MVP),
`subtaskClaimTtlMs: 120000`, номера полей — `null`.

**Номера полей подзадачи не настраиваются и не имеют значений по умолчанию: они ищутся по
имени** в описании формы (`GET /forms/{id}`), как `receiveWebhook` уже ищет «Юнит» и
«Компонент» в отвечаемой задаче. Причина в логах: копия продовой формы перенумеровала всё —
«Юнит» стал 35 вместо 97, «Компонент» 28 вместо 36, «Эл. почта» 44 вместо 5, «Тема» 47
вместо 1, «Сообщение» 48 вместо 2, а поля 97 не существует вовсе. Pyrus отвечал 400 на
создание подзадачи, оба раза. Имена задаются в `const FIELD_NAMES` и переопределяются через
`config.fieldNames`; номер в `config` (`unitFieldId` и прочие) по-прежнему побеждает имя —
это аварийный выход, если поле назвали неожиданно.

**`config.botAuthorIds`** — список id наших сервисных аккаунтов, `[1314929]` по умолчанию
(`botAuthorId` в единственном числе тоже работает). Резервного признака «email начинается
на `bot@`» больше нет: в этой организации Pyrus такой email у КАЖДОГО бота, и резерв
признавал своим `bot techSupport Supervisor`, `Approver` и ботов других проектов — виток
отбрасывался как «мой собственный комментарий», а в истории для промпта чужие реплики
подписывались «Ассистент».

**`config.forms`** — входящий whitelist. MVP разрешает только
`{ "2430464": { "role": "chat", "environment": "test" } }`; даже явно настроенная роль
`ticket` безусловно игнорируется. Если документ отсутствует, код использует тот же
единственный тестовый id `2430464`, а не принимает любую или продуктивную форму. Читает
`receiveWebhook`, результат кладёт в `runtime.role`.
`knowledgeExecution: "partner_answer"` — отдельное разрешение форме отправлять партнёру
ответы веток с таким же режимом в статье. Без точного значения используется
`handover_only`: вопросы можно собрать, но найденный совет попадёт только оператору.

**`config.kcFieldNames`** — имена поля, заполненность которого означает «заявка из
колл-центра», по умолчанию `["Id задачи из КЦ"]`. Такой тикет бот не ведёт: партнёра в задаче
нет, переписка только внутренняя.

**`config.rag`** — как подбирается тема:

| Поле | Смысл |
|---|---|
| `mode` | `off` — только по словам; `shadow` — базу знаний спрашиваем и печатаем в лог, решает подбор по словам; `on` — решает база знаний, слова остаются страховкой. **По умолчанию `off`**; `shadow` и `on` включаются только явно для эксперимента |
| `minScore` | ниже этого счёта кандидат не рассматривается, по умолчанию `0` |

Порядок включения именно такой и не иначе: шкала счёта у каждой базы знаний своя, порог
наугад не ставится. В `shadow` каждый виток маршрутизации печатает строку
`searchKnowledge: маршрут …` — что нашли слова, что нашёл RAG, каков **отрыв** первого
кандидата от второго и кто принял решение. По ней и подбирается `minScore`, после чего
`mode` переводится в `on`.

Порог обязателен. Семантический поиск всегда возвращает ближайшее — «ничего не нашлось» у
него нет, — и при `minScore: 0` любое постороннее обращение уедет в ближайшую статью вместо
оператора. Отрицательные примеры в `tests/routing.cases.json` существуют ровно для того,
чтобы порог не настроили в ноль.

**Прежде чем включать `on`, база знаний должна быть наполнена.** Пустая отвечает ошибкой
`Empty response body during chunks retrieval` — бот это переживает (откат на подбор по словам,
в логе `RAG: недоступен`), но пользы от режима не будет никакой. Документы собираются
генератором `node tools/build-knowledge.js`, дальше содержимое `docs/rag/` загружается в
базу знаний руками, имя файла = имя источника = `key` статьи. Тот же запуск создаёт payload
каталога для БД и манифест хешей: отдельно собирать RAG больше нельзя.

Если RAG доступен и вернул фрагменты, но все они ниже `minScore`, это теперь окончательный
ответ «тема не найдена»: подбор по словам не запускается повторно и не отменяет порог.
Запасной подбор используется только когда RAG недоступен или вернул действительно пустой
ответ. В логе эти состояния различаются: `недоступен`, `пустой ответ`, `всё ниже порога`.

### Что известно о шкале счёта

Два измеренных запроса (7 статей в базе):

| запрос | RAG | подбор по словам |
|---|---|---|
| «нужен стол для раскатки пиццы для пиццерии Додо» | no_internet **3.87**, equipment_request 2.46, dodo_is_slow 2.10 — далее обрыв к 0.66 | no_internet 0.75, employee_card_change 0.50 — верной статьи нет вовсе |
| «оборвалось соединение с сетью, ничего не открывается» | no_internet **2.48**, rating_appeal_rejected 2.31, support_complaint 1.69 — далее обрыв к 0.71 | no_internet 1.00 — одна, верная |

Три вывода, каждый важен для настройки.

**Абсолютный счёт несравним между запросами.** 2.48 здесь — верное первое место, 2.46 там —
верное второе, 3.87 там же — неверное первое. Порог не может отличать правильное от
неправильного, и ставить его с этой целью бессмысленно.

**Зато шумовой уровень устойчив: 0.59–0.71 в обоих запросах.** Статьи, не имеющие к запросу
никакого отношения, ложатся в эту полосу. Отсюда и назначение порога — **отсечь шум, а не
выбрать победителя**: `minScore: 1.0` уверенно выше шума и не трогает осмысленных кандидатов.
Выбор из 2–3 кандидатов по их описаниям — работа маршрутизатора, и она именно так и задумана.

**Поиск не чисто лексический.** `rating_appeal_rejected` получила 2.31 при **нуле** общих слов
с запросом (ни точных, ни по основе), тогда как `pos_down` с девятью вхождениями «не» осталась
на 0.71. Значит есть смысловая составляющая, но грубая: отрыв верной статьи от совершенно
посторонней составил 0.16.

**Отдельного поля связи нет и не требуется.** `createSubtask` передаёт `parent_task_id`
прямо в `POST /tasks` и не трогает поле `95`, занятое интеграцией колл-центра. Параллельные
webhook-прогоны арбитрирует атомарный `subtaskClaim` в документе задачи. При потерянном
ответе Pyrus созданная задача восстанавливается по `linked_task_ids` и идентификатору
обращения внутри обязательного поля «Сообщение». `subtaskClaimTtlMs` задаёт, через сколько
можно восстанавливать результат зависшего запуска. Если связанная задача не найдена,
повторное создание запрещено и обращение передаётся оператору.

Поля исходного чата (`unitFieldId`, `componentFieldId`) приходят в вебхуке и живут в
`state:<taskId>.runtime` — их настраивать не нужно.

## 7. Как проверять правки

- **`node tests/run.js`** — полный набор проверок без зависимостей и без деплоя; актуальное
  число печатается в финальной строке прогона: синтаксис всех
  функций в той же async-обёртке, что на платформе, кавычки в YAML, связность графа,
  статьи каталога знаний, синхронность исходников/каталога/RAG/манифеста, совпадение восьми
  копий `writeState` и поведение функций на
  заглушках `Db`, `Http`, `Log`, `Context`, `AgentContext`.
  Заглушка `Db` воспроизводит и то, чем платформа однажды стоила боту всех записей:
  фильтры по содержимому `value`, возврат `count`, отсутствие upsert, отказ на массив в
  `$set` и конфликт родительского и дочернего путей в одной операции. Дополнительно
  запрещены Unicode property escapes в регулярных выражениях:
  Node.js их компилирует, а движок Agent Platform — нет. Зелёный прогон больше не может
  значить, что запись работает только в тестах.
- **`node tests/catalog.check.js`** — реальный каталог по всем сценариям, см. 4.4.
- **`node tests/routing-catalog.test.js --report`** — каждый положительный запрос из
  `routing.cases.json` должен находить ожидаемую тему первой запасным поиском; для
  отрицательных запросов отчёт показывает ложных кандидатов, которых обязан отвергнуть
  routing-agent. Смысловые оценки RAG по-прежнему получают только живым прогоном.
- **Критические строки промптов проверяются статически, качество смысла — нет.** Полный
  ответ реальной модели проверяется только прогоном в Pyrus и чтением логов. Поэтому выводы
  из живых прогонов оседают либо в контрактных запретах, либо, что надёжнее, в коде.

## 8. Чего лучше не трогать

- **`parseAgentJson`, `parseTurnInterpretation` и `parseResponseComposition` —
  предохранители, а не formality.** Первый проверяет обычные роли, второй не даёт
  смысловому агенту выйти за id/value/цитату, третий связывает формулировку с текущим
  `responsePlan` и откатывает небезопасный результат Composer к разрешённому плану.
  Здесь каталог остаётся арбитром: `topicKey` сверяется с ключами статей, `componentName` — со
  значениями оттуда же, юнит — с `unitCatalog`, а ответы — с ключами, которые статья
  объявила. Несуществующее в документ не пишется: неверное значение в поле Pyrus хуже
  пустого.
- **В Pyrus пишет только `finalize`** — единственное исключение `createSubtask`, который
  создаёт саму подзадачу.
- **Запись в БД — только через `writeState`** своей функции: фильтр по `taskId`, `$set`
  без префикса `value.`, проверка `count`, целый документ как фолбэк. Прямой вызов
  `Db.updateByFilters` однажды потерял целый виток диалога, молча.
- **Каждая функция пишет только свои пути.** Запись документа целиком возвращает факты в
  состояние на момент своего чтения и теряет всё, что успел собрать параллельный виток.
