# Переход к двум средам

Согласовано 5 сентября 2026: `PyrusTechSupportOperator-dev` / `dev` для разработки,
существующий `PyrusTechSupportOperator` / `main` для будущего prod.
**Обе среды пока тестовые. Реальные формы не подключены и этим изменением не разрешены.**

## Подготовленная часть

- `tools/environments/dev.json` и `prod.json` — проверяемые публичные привязки ветки,
  проекта, webhook и БД. Секретов в этих файлах нет.
- `docs/environments/*-config.json` — стартовые шаблоны config для новых сред.
  Оба содержат только тестовые формы и `handover_only`.
- `tools/deploy.ps1 -Environment dev|prod` требует явную среду, проверяет текущую ветку,
  привязки до и после слияния экспорта, сохраняет docs/tests/tools и запускает проверки.
- `-Environment dev -BootstrapDev` может **один раз создать** отсутствующую удалённую
  ветку dev. В начальной версии URL старого Pyrus webhook должен быть null.
  Это исключение для передачи исходных файлов новому проекту, не разрешение публикации.
- После создания ветки обычный deploy dev остаётся заблокирован до проверки первого
  экспорта и регистрации новых привязок.

Профиль `prod` пока имеет lifecycle `preproduction`; `dev` зарегистрирован как `test`
после первого экспорта `1d682dc`. Серверные данные и доступы ещё не проверены.
Переход к реальным формам, включение ответов и промышленный выпуск остаются отдельной
работой. Проверка файлов не проверяет содержимое БД или реальные права доступа.

## Создание проекта — выполнено

Проект создан, экспорт получен и проверен. Новые привязки зарегистрированы;
следующее действие — [запуск проверки настроек dev](dev-first-export-review.md).
Ниже сохранён порядок начального создания.

1. Создать **новый** проект `PyrusTechSupportOperator-dev` с хранением в Git:
   `https://github.com/RubtsovAndrey/PyrusTechSupportOperator`, ветка **dev**.
   Использовать содержимое репозитория как исходную версию, без выбора шаблона,
   перезаписывающего ветку. Текущий проект и его подключение к main сохранить.
2. Пока не публиковать dev и не переключать на него webhook формы Pyrus.
   Начальные файлы ещё содержат идентификаторы исходного проекта и требуют проверки
   преобразования платформой. У webhook специально убран старый URL.
3. В новом проекте выполнить **Commit & push**, чтобы получить его первый экспорт.
   Сообщить, что проект создан и экспорт отправлен. Секреты в переписку не передавать.

После этого Codex сравнит manifest, новый webhook, интеграции, origin-key и ссылки
в коде, восстановит защищённые каталоги и зарегистрирует привязки dev.
Если платформа оставит исходную идентичность проекта или не создаст новый webhook,
публикация остаётся заблокированной; дальнейшие действия будут определены по экспорту.

## Настройка среды после проверки экспорта

У dev должна быть собственная БД с областью PROJECT. Нельзя подключать общую БД
с состояниями действующей среды. В новой БД нужны:

- `config` для тестовых форм с проверенными botAuthorIds и при необходимости настройками
  полей; шаблон — основа, а не команда перезаписать существующий config;
- `knowledge_catalog` из выбранной версии `docs/knowledge_catalog.json`;
- необходимые справочники, если они используются текущей конфигурацией.

Не копировать `state:*`, claims, старые токены и прочие записи исполнявшихся диалогов.
Git не переносит содержимое БД и значения секретов. Доступ к MCP БЗ и LLM настраивается
в новом проекте отдельно и проверяется до первого чата.
В текущем Pyrus webhook access_token приходит в payload: наличие старой записи
`pyrus-token` в экспорте само по себе не подтверждает правильного подключения Pyrus.

После проверки настроек опубликовать dev, затем переключить webhook **тестовой** формы
на новый адрес. Одну форму должен обслуживать один проект: старое подключение тестовой
формы отключить при переключении. Во время перехода оба проекта не должны отвечать
одному и тому же чату. Будущий prod остаётся без реальных обращений до отдельной приёмки.

## Стенд Selector в dev

Следующий этап после регистрации dev: отдельный тестовый триггер, который принимает id
зафиксированного случая, запускает ту же реализацию Selector и сохраняет результаты.
Он не соединяется с Pyrus Actions и не использует state реального обращения. Примеры
с исходными статьями хранятся отдельно от Git. Обычные тестовые чаты продолжают проверять
полный путь; стенд проверяет модели на неизменных входах.

Добавлен отдельный тестовый триггер **Dev - check setup**, который проверяет настройки
нового окружения. Сам стенд повторов Selector пока **не добавлен**. Сохранены входы и протокол эксперимента:
[`terra-selector-empty-live-review-2026-09-05.md`](terra-selector-empty-live-review-2026-09-05.md).

## Перенос версии dev → main

Обычный merge всей ветки пока не является готовой командой релиза. Первый экспорт
подтвердил разные manifest, URL webhook и ключи интеграций/credentials, включая их
замену внутри кода. Требуется перенос общей логики с сохранением привязок целевой среды.

Правила будущего выпуска:

1. Зафиксировать проверенный commit dev и версию каталога сценариев.
2. Подготовить изменение main с сохранением его идентичности и подключений; dev-триггер
   экспериментов не должен становиться активным входом prod.
3. Пройти локальные проверки и приёмку выбранных сценариев; настройки prod и содержимое
   его БД не заменять настройками dev.
4. Push в main, Pull в соответствующем проекте, проверить импорт, опубликовать и сверить
   runtime. Перед публикацией сохранить предыдущую версию кода и каталога для возврата.

Пока реальных форм нет, отрепетировать этот процесс между двумя тестовыми средами.
Изменения prepared-сценариев в БЗ также должны иметь тестовую и опубликованную версии.
Общая справочная БЗ остаётся общей для чтения, согласно принятому принципу актуальных знаний.

## Команды после регистрации привязок

```powershell
pwsh -NoProfile -File tools/deploy.ps1 -Environment dev
pwsh -NoProfile -File tools/deploy.ps1 -Environment prod
```

Каждая команда запускается только из соответствующей ветки. Отправка в Git не подтверждает
Pull, публикацию или настройку серверной БД. На текущем этапе `prod` означает main тестового
проекта, а не разрешение работы с реальными формами.
