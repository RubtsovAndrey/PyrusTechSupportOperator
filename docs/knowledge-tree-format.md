# Формат статьи БЗ: дерево диалога

Реализовано и покрыто тестами (`node tests/run.js`, набор «knowledge tree»).

Статья без поля `nodes` работает по-старому (`steps`, `preQuestions`, `route`,
`onFail`), поэтому существующие статьи ничего не теряют и переписывать их не нужно.

## Узел

Все узлы имеют одну форму. Любое поле необязательно, кроме того, что узел должен
куда-то вести.

```
{
  "advice": "текст, который получит партнёр",
  "ask": [ { "key": "имя_поля", "question": "о чём спрашиваем" } ],
  "branches": [ { "when": ["слова партнёра", "синонимы"], "go": "идентификатор_узла" } ],
  "else": "идентификатор_узла",
  "go": "идентификатор_узла",
  "end": "close | subtask | escalate",
  "componentName": "компонент подзадачи"
}
```

- **`ask`** — вопросы задаются одним сообщением, все сразу. Больше трёх в узле не
  стоит: партнёр ответит на первые два. Ответы сохраняются под своими `key` и уходят
  в подзадачу или во внутреннюю переписку при эскалации.
  Спрашивается только то, чего ещё нет, и **один раз**: если партнёр на вопрос не
  ответил, статья идёт дальше без этого поля, а не держит его в диалоге. Поля
  необязательные по решению — полнота на совести партнёра.
- **`key`** — без точек и `$`: такой ключ адресовал бы не то место в документе задачи,
  чем выглядит, поэтому он отбрасывается. То же про идентификаторы узлов.
- **`branches`** — ветка выбирается **только из перечисленных**. Слова `when` — не только
  подсказка модели: **сначала их сопоставляет код** с ответами, которые собрал сам этот
  узел. Спросили «что именно изменить», партнёр сказал «фамилию», ветка объявлена как
  `["фамилия", "имя", "ФИО"]` — решение принимается без витка модели. Словоформы
  сравниваются по основе («фамилию» = «фамилия», «стажа» = «стаж»), а многословная
  подсказка считается совпавшей только целиком: «номер документа» не есть «номер
  телефона». Слова короче трёх букв не опознают ничего, а короткие слова, у которых
  меняется сама основа, стоит перечислить формами: «имя» и «имени» для кода — разные
  слова, и второе придётся добавить в `when` руками. Если ни одна
  ветка так не опозналась или опозналось сразу две разных — выбирает модель, и её
  ответ тоже проверяется по узлу: ветки, которой нет в списке, не существует. Синонимов
  можно перечислить сколько угодно — чем их больше, тем реже требуется модель.
- **`else`** — куда идти, если ни одна ветка не подошла. Без него непонятый ответ
  уходит к оператору.
- **`advice` без `ask`** — бот даёт рекомендацию и спрашивает, помогло ли. «Помогло» →
  чат закрывается. «Не помогло» → узел из `onFail` этого узла, а если его нет — из
  `onFail` статьи.
- **`end`** — конец: `close` закрыть чат, `subtask` создать подзадачу, `escalate`
  передать оператору вместе со всем собранным.
- **`onFail` на узле** — куда идти, если партнёр сказал «не помогло». Может назвать
  другой узел — тогда диалог остаётся у бота. Если названный узел только заканчивает
  диалог, бот переходит к концу сразу, не расходуя лишний виток модели.
- **`route` у статьи с `nodes` игнорируется** — она всегда входит через солвер, иначе
  маршрут в подзадачу проскочил бы мимо всех вопросов, ради которых дерево и заведено.

## Статья

```
{
  "key": "идентификатор",
  "description": "по этому тексту тема находится по словам партнёра",
  "start": "идентификатор_первого_узла",
  "onFail": "escalate | идентификатор_узла",
  "askBeforeHandover": [ { "key": "...", "question": "..." } ],
  "nodes": { "идентификатор": { ... } }
}
```

**`askBeforeHandover`** — вопросы, которые задаются перед любым `subtask` или
`escalate`, в какой бы ветке те ни оказались. Ровно для правил вида «всегда уточняем
причину». Задаются **после** вопросов самой ветки и только один раз: спрошенная раньше
причина изменения приходила бы до того, как выяснено, что менять.

Ответы принимаются только под теми ключами, которые статья объявила в `ask` или
`askBeforeHandover`. Ключ, которого в статье нет, не сохраняется — иначе модель в
плохой день насыпала бы в документ задачи полей, которых никто не читает.

**Сказанное раньше второй раз не спрашивается.** Партнёр часто выкладывает всё в первом
сообщении: «нужно изменить фамилию сотрудника Иванов Иван на Петров Иван, ошиблись
при заведении карточки» — здесь есть ответы на все вопросы темы 1. Модель передаёт такие
ответы в `searchKnowledge` тем же вызовом, которым берёт статью — параметр `answers`
обязательный именно для этого; ключи проверяются по статье, что и всегда. Спрашивается
остаток: вопрос сжимается, а если остатка нет — статья идёт дальше сама, пока её
ветки читаются из собранных ответов. Пример выше укладывается в **один виток** вместо
четырёх: вопросы узла уже отвечены, ветка «фамилия» опознана по словам самого ответа,
причина тоже есть — сразу подзадача.

В статье имеет смысл перечислять в `when` те слова, которыми партнёр отвечает на вопрос
этого же узла, а не названия веток для внутреннего употребления: именно по ним ветка
опознаётся без модели.

Юнит и общее описание проблемы спрашивать в дереве не нужно: их собирает общий
приёмный этап до того, как тема вообще определена. Это уже работает.

## Тема 1. Изменение данных в карточке сотрудника

```json
{
  "key": "employee_profile_change",
  "description": "изменить данные сотрудника в карточке: телефон, фамилия, ФИО, стаж, перевод в другую пиццерию, аватарка, фото",
  "start": "what",
  "onFail": "escalate",
  "askBeforeHandover": [
    { "key": "reason", "question": "по какой причине нужно внести это изменение" }
  ],
  "nodes": {
    "what": {
      "ask": [
        { "key": "employee", "question": "ФИО сотрудника, которого касается изменение" },
        { "key": "changeKind", "question": "что именно нужно изменить в карточке" }
      ],
      "branches": [
        { "when": ["аватарка", "фото", "фотография", "аватар"], "go": "avatar" },
        { "when": ["телефон", "номер телефона", "мобильный"], "go": "phone" },
        { "when": ["фамилия", "имя", "имени", "ФИО", "опечатка в фамилии"], "go": "name" },
        { "when": ["стаж", "дата приёма", "опыт"], "go": "tenure" },
        { "when": ["перевод", "другая пиццерия", "другая точка"], "go": "transfer" }
      ],
      "else": "otherField"
    },

    "avatar": {
      "advice": "ЗАПОЛНИТЬ: аватарку сотрудник меняет самостоятельно — интерфейс и адрес.",
      "end": "close"
    },

    "phone": {
      "ask": [{ "key": "newValue", "question": "на какой номер нужно поменять" }],
      "end": "subtask",
      "componentName": "ЗАПОЛНИТЬ: компонент"
    },

    "name": {
      "ask": [{ "key": "newValue", "question": "как правильно должны быть записаны фамилия и имя" }],
      "end": "subtask",
      "componentName": "ЗАПОЛНИТЬ: компонент"
    },

    "tenure": {
      "ask": [{ "key": "newValue", "question": "какой стаж или дату приёма нужно указать" }],
      "end": "subtask",
      "componentName": "ЗАПОЛНИТЬ: компонент"
    },

    "transfer": {
      "ask": [{ "key": "newValue", "question": "в какую пиццерию или кофейню нужно перевести сотрудника" }],
      "end": "subtask",
      "componentName": "ЗАПОЛНИТЬ: компонент"
    },

    "otherField": {
      "ask": [{ "key": "newValue", "question": "какое поле и на какое значение нужно поменять" }],
      "end": "subtask",
      "componentName": "ЗАПОЛНИТЬ: компонент"
    }
  }
}
```

Текущее значение поля нигде не спрашивается — вы сказали, что его видно в профиле.
Причина спрашивается один раз перед подзадачей и не спрашивается в ветке с аватаркой,
потому что там подзадачи нет.

## Тема 2. Нет интернета

```json
{
  "key": "no_internet",
  "description": "нет интернета в пиццерии или кофейне, не работает Додо ИС, не открывается касса и сайт",
  "start": "scope",
  "onFail": "escalate",
  "nodes": {
    "scope": {
      "ask": [{ "key": "scope", "question": "не работает только Додо ИС или интернет целиком — например, не открываются и другие сайты" }],
      "branches": [
        { "when": ["интернет целиком", "вообще ничего не работает", "другие сайты тоже"], "go": "isp" },
        { "when": ["только Додо ИС", "остальное работает", "интернет есть"], "go": "dodo" }
      ],
      "else": "dodo"
    },

    "isp": {
      "advice": "ЗАПОЛНИТЬ: связь обеспечивает провайдер, восстановить её с нашей стороны нельзя — что именно порекомендовать партнёру.",
      "ask": [{ "key": "moreHelp", "question": "остались ли вопросы, с которыми я могу помочь" }],
      "branches": [
        { "when": ["вопросов нет", "спасибо, всё", "понятно"], "go": "close" },
        { "when": ["да, остались", "есть ещё вопрос"], "go": "operator" }
      ],
      "else": "operator"
    },

    "dodo": {
      "ask": [{ "key": "symptom", "question": "что именно происходит в Додо ИС: не открывается совсем, показывает ошибку или сильно тормозит" }],
      "go": "operator"
    },

    "close": { "end": "close" },
    "operator": { "end": "escalate" }
  }
}
```

Здесь `else` у первого узла ведёт в ветку Додо ИС осознанно: если партнёр ответил
непонятно, безопаснее разбираться дальше, чем отправить его к провайдеру.

## Тема 5. Не приняли апелляцию по рейтингу

```json
{
  "key": "rating_appeal_rejected",
  "description": "не приняли апелляцию по рейтингу, отклонили апелляцию, не согласны с отказом по апелляции",
  "start": "which",
  "onFail": "escalate",
  "nodes": {
    "which": {
      "ask": [{ "key": "ratingKind", "question": "речь о рейтинге стандартов или о рейтинге клиентского опыта" }],
      "branches": [
        { "when": ["стандартов", "рейтинг стандартов", "стандарты"], "go": "standards" },
        { "when": ["клиентского опыта", "клиентский опыт", "NPS"], "go": "cx" }
      ],
      "else": "operator"
    },

    "standards": {
      "ask": [
        { "key": "appeal", "question": "когда подавали апелляцию и по какому пункту" },
        { "key": "argument", "question": "почему считаете отказ несправедливым" }
      ],
      "end": "subtask",
      "componentName": "ЗАПОЛНИТЬ: компонент рейтинга стандартов"
    },

    "cx": {
      "ask": [
        { "key": "appeal", "question": "когда подавали апелляцию и по какому заказу или отзыву" },
        { "key": "argument", "question": "почему считаете отказ несправедливым" }
      ],
      "end": "subtask",
      "componentName": "ЗАПОЛНИТЬ: компонент клиентского опыта"
    },

    "operator": { "end": "escalate" }
  }
}
```

Это тема, из-за которой компонент переезжает с темы на ветку: у двух рейтингов он
разный, а тема одна.

## Тема 7. Не работает касса — каркас

Инструкций по кассам у меня нет, поэтому здесь только структура ветвления: сколько
шагов, где спрашиваем, где советуем, где отдаём оператору. Тексты рекомендаций и
реальный список моделей и ошибок за вами.

```json
{
  "key": "pos_down",
  "description": "не работает касса, касса не печатает чек, ошибка на кассе, касса не включается, не проходит оплата картой",
  "start": "symptom",
  "onFail": "operator",
  "nodes": {
    "symptom": {
      "ask": [{ "key": "symptom", "question": "что именно происходит с кассой" }],
      "branches": [
        { "when": ["не включается", "нет питания", "чёрный экран"], "go": "dead_model" },
        { "when": ["не печатает чек", "не выходит чек", "нет печати"], "go": "print_model" },
        { "when": ["ошибка на экране", "выдаёт ошибку", "код ошибки"], "go": "error_model" },
        { "when": ["не проходит оплата", "не принимает карту", "терминал"], "go": "payment_model" },
        { "when": ["зависает", "тормозит", "не отвечает"], "go": "freeze_model" }
      ],
      "else": "operator"
    },

    "dead_model": {
      "ask": [{ "key": "model", "question": "какая касса — модель или как она подписана" }],
      "go": "dead_advice"
    },
    "dead_advice": {
      "advice": "ЗАПОЛНИТЬ: что проверить, если касса не включается.",
      "onFail": "operator"
    },

    "print_model": {
      "ask": [{ "key": "model", "question": "какая касса и что показывает при попытке печати" }],
      "go": "print_advice"
    },
    "print_advice": {
      "advice": "ЗАПОЛНИТЬ: что проверить, если чек не печатается.",
      "onFail": "operator"
    },

    "error_model": {
      "ask": [
        { "key": "model", "question": "какая касса" },
        { "key": "errorText", "question": "какой текст или код ошибки на экране" }
      ],
      "branches": [
        { "when": ["ЗАПОЛНИТЬ: код известной ошибки"], "go": "known_error_advice" }
      ],
      "else": "operator"
    },
    "known_error_advice": {
      "advice": "ЗАПОЛНИТЬ: что делать при этой ошибке.",
      "onFail": "operator"
    },

    "payment_model": {
      "ask": [{ "key": "model", "question": "какой терминал оплаты и что он показывает" }],
      "go": "operator"
    },

    "freeze_model": {
      "ask": [{ "key": "model", "question": "какая касса и после каких действий зависает" }],
      "go": "freeze_advice"
    },
    "freeze_advice": {
      "advice": "ЗАПОЛНИТЬ: что проверить при зависании.",
      "onFail": "operator"
    },

    "operator": { "end": "escalate" }
  }
}
```

Обратите внимание на узел `error_model`: он и собирает данные, и ветвится по ним. Если
таких известных ошибок с готовым решением наберётся много, ветки растут списком, а всё
неопознанное уходит оператору через `else`.

## Темы, которым дерево не нужно

- **Тема 6 (предложение о нововведении)** — один узел: спросить описание, `end: "subtask"`.
- **Тема 8 (маркетинговый цикл)** — один узел: `advice` с базовым ответом, `end: "close"`.
- **Тема 9 (неизвестный вопрос)** — статьи нет вовсе, работает текущая эскалация с
  простановкой юнита в поле задачи.

## Что осталось заполнить вам

Все `ЗАПОЛНИТЬ` выше: тексты рекомендаций, адрес интерфейса для аватарки, названия
компонентов и реальный список моделей касс и их ошибок. Структура ветвления работает и
без них — она просто передаст обращение оператору там, где текста нет.

## Как это устроено внутри

Ход по дереву хранится в документе задачи: `data.treeNode` — узел, на котором стоит
партнёр, `data.treeAnswers` — собранные ответы, `data.treeEnd` — терминал, если дошли.
Один узел за один виток диалога.

Ветку выбирает модель, но двумя вызовами инструмента: первым `searchKnowledge` отдаёт
узел и список ветвей, вторым получает выбранную ветку и отдаёт уже содержимое следующего
узла. Модель никогда не видит содержимое двух ветвей одновременно — иначе она склеивает
их в один ответ, чем этот проект уже болел.

Предохранитель от петли считает не вопросы, а продвижение: вопрос из узла, на котором
диалог ещё не стоял, — прогресс; вопрос из того же узла повторно — петля, и после трёх
таких подряд обращение уходит оператору. Сверху стоит жёсткий предел в 12 вопросов на
статью: дерево глубже — ошибка в статье, и платить за неё партнёр не должен.
