## 🎯 Рекомендации по формату метаданных

### Вариант 1: YAML в code block ⭐ **РЕКОМЕНДУЕТСЯ**

```markdown
# Проблемы с кассой: смена превысила 24 часа

\`\`\`yaml metadata
component: POS
route: solver
onSuccess: close
onFail: operator
requiresSubtask: false
\`\`\`

## Симптомы
...
```

**Преимущества:**
- ✅ Легко парсить
- ✅ Видно в UI БЗ
- ✅ Можно редактировать вручную
- ✅ Не мешает основному тексту

### Вариант 2: JSON в code block

```markdown
\`\`\`json config
{
  "component": "POS",
  "route": "solver"
}
\`\`\`
```

### Вариант 3: Топики (НЕ рекомендуется)

Топики вида `component:POS`, `route:solver`

**Недостатки:**
- ⚠️ Видны всем пользователям БЗ
- ⚠️ Смешиваются с обычными тегами
- ⚠️ Нет валидации

## 🔧 Реализованные утилиты

### 1. `tools/mcp-client.js`
MCP-клиент для работы с Базой Знаний:
- `MCP.currentUser()` — информация о пользователе
- `MCP.getSpaces()` — список пространств
- `MCP.searchContent(query, spaceIds)` — поиск статей
- `MCP.getContent(articleId)` — получить статью
- `MCP.createContent(...)` — создать статью (требует write)
- `MCP.updateContent(...)` — обновить статью (требует write)
- `MCP.deleteContent(...)` — удалить статью (требует write)

### 2. `tools/parse-metadata.js`
Парсинг метаданных из статей:
- `parseMetadataFromMarkdown(markdown)` — из YAML-блока
- `parseMetadataFromTopics(topics)` — из топиков
- `parseArticleMetadata(article)` — комбинированный
- `parseRoutingScenarios(markdown)` — сценарии маршрутизации

### 3. `tools/test-mcp-simple.js`
Упрощённый тест для проверки работы MCP

## 💡 Ответы на вопросы

### 1. Расход токенов?
**НЕТ!** MCP — это обычный HTTP API. Токены LLM расходуются только при генерации ответов агентами.

### 2. Как работает поиск?
**Полнотекстовый поиск** в PostgreSQL (FTS). Без вызовов LLM, без embedding-моделей.

### 3. Стоимость изменится?
**НЕТ!** Количество витков, длина контекста и вызовы LLM остаются прежними.

### 4. Формат метаданных?
**YAML в code block** — самый удобный и читаемый вариант.
