## Следующее действие в интерфейсе dev

После отправки подготовленной версии:

1. В `PyrusTechSupportOperator-dev` выполнить **Pull**.
2. Выбрать **Тестировать → Dev - check setup**.
3. В открывшемся тестовом виджете отправить `проверка`, если запуск не произошёл
   автоматически через `/start`.
4. Открыть результат функции **Dev - inspect configuration and access** в панели
   выполнения и передать результат либо выгрузить логи теста.

Для этой проверки публикация и подключение формы Pyrus не нужны. Функция требует
тестовый канал и правильный project-key. При несовпадении остановится до доступа к БД
и интеграциям; если интерфейс запуска передаст другой тип канала, нужно изучить трассу,
а не убирать ограничение вслепую.

## Что проверяет inspectDevSetup

| Поле результата | Что означает успешный результат |
|---|---|
| `config: ok` | Присутствуют только две тестовые формы, нужные роли и handover_only |
| `catalog: present`, `topicCount` | Есть непустой каталог; это ещё не проверка совпадения версии |
| `kbCredential: present` | CUSTOM credential доступен и содержит непустой токен |
| `kbToolDiscovery: ok` | MCP tools/list доступен и объявляет search_content/get_content |
| `defaultModel: ok` | GPT-4.1-mini ответила на минимальный запрос без инструментов |
| `selectorModel: ok` | Terra ответила на такой же запрос |

`missing`, `unavailable`, `review_required` и `failed` показывают недостающую настройку
или отказ. Отчёт не включает значения credentials, тексты статей и сообщения исключений.
Функция не пишет config, state или каталог, не вызывает Pyrus и не меняет чат.
Выполняются два реальных коротких LLM-запроса, каждый с лимитом 512 токенов.

Эта проверка не подтверждает доступ к каждой статье, правильность botAuthorIds,
версию knowledge_catalog, работу полного диалога или готовность к публикации.
Это проверка настройки нового окружения; отдельный стенд повторных запусков Selector
на зафиксированных статьях добавлен; первая живая серия `success-full` дала 5/5,
остальные три серии ожидаются.
