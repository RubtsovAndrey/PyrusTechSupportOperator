# Стенд повторов Operator Evidence Selector

Подготовлен 5 сентября 2026 в dev. Первая живая серия `success-full` завершилась 5/5
полезных отборов; [разбор](selector-eval-success-full-2026-09-05.md). Остальные три серии
ещё ожидаются. Настройка dev подтверждена отдельной трассой
`dev_second_test/all-logs-1788627024397.json`.

Первый импорт стенда выявил обязательность `falseStep` в BotDeployRequest:
`false-step: null` у `Evaluation case ready?` блокировал сборку. Исправлено подключением
к завершающему `Evaluation idle`. Локальная проверка графа теперь отклоняет условия
без заполненного выхода `false`; `/start` проходит через этот блок без вызова модели.

Выгрузки `dev_terra_test_one` и `dev_terra_test_two` содержали четыре команды, но каждый
раз исполнялся `inspectDevSetup`: Selector не вызывался. Причина сохранения этого входа
по трассам не установлена. Добавлен маршрут перед диагностикой: четыре точные команды
эксперимента теперь запускают Selector также через **Dev - check setup**. В этой ветке
не выполняются предварительные MCP/LLM-пробы диагностики. Остальные сообщения в этом
входе сохраняют прежнюю проверку настроек. Исправление подтверждено трассой
`dev_terra_success_full/all-logs-1788633316977.json`.

## Запуск в интерфейсе

1. В проекте **PyrusTechSupportOperator-dev** выполнить **Pull** из ветки `dev`.
2. Открыть **Базы данных → Pyrus Bot Database** этого проекта. Создать документ с ключом
   `selector_eval_cases`. В значение вставить весь JSON из подготовленного локального
   файла `/tmp/pyrus-selector-eval-cases.json`, без дополнительной обёртки key/value.
3. Выбрать **Тестировать → Dev - Selector evaluation**; четыре команды также принимаются
   через **Dev - check setup** после Pull исправления маршрута. В прямом входе Selector автоматический `/start` не
   выполняет модельных запросов; он только выводит подсказку в лог.
4. Сначала отправить только `success-full`. Дождаться завершения **Collect sample 5** и
   строки `selectorEval.report` в логах. Если выполняется лишь проверка настроек,
   исправленный маршрут ещё не применяется. Выгрузить трассу первого запуска для проверки.
5. Аналогично отправить по одному `empty-full`, `empty-single`, `noise-only`, каждый раз
   дожидаясь окончания и сохраняя логи. Если запуск оборвался, сохранить его трассу
   для разбора, прежде чем повторять.

Каждая команда вызывает Terra пять раз: весь набор — **20 реальных модельных запросов**.
Результат находится в панели выполнения и БД; текстовый ответ в виджет не отправляется.
Для этого эксперимента публикация и подключение Pyrus не требуются.

## Что сравниваем

| Команда | Вход | Ожидание |
|---|---|---|
| `success-full` | Вопрос и все кандидаты успешного чата `377354226` | Выбрана цитата из карточки сотрудника о фото 300×300 |
| `empty-full` | Вопрос и все кандидаты чата `377356362`, где Terra вернула пустой отбор | Та же полезная цитата |
| `empty-single` | Второй вход, оставлена только карточка сотрудника | Та же полезная цитата без влияния других статей |
| `noise-only` | Второй вход без карточки сотрудника | Пустой отбор |

Используются существующие `selectOperatorEvidence` и `parseOperatorEvidence`, та же
модель и лимит 8192 токена, что в чате. Во всех пяти повторах одной команды модель
получает одинаковый запрос; предыдущие ответы и ожидаемый результат в него не входят.
Тексты статей и их порядок сохранены. Привязки к задаче и комментарию заменены
синтетическими идентификаторами, поэтому это контролируемый повтор содержания входа,
а не буквальное воспроизведение всех байтов исходного чата.

## Результаты и границы проверки

`selectorEval.sample` содержит статус, выбранные статьи с проверенными цитатами,
`expectedMet` и длительность. `selectorEval.report` суммирует пять повторов, фиксирует
модель, лимит и SHA-256 вопроса с кандидатами. Статусы различают `selected`,
`no_evidence`, `invalid`, `transport_error` и `parser_error`.

Автоматический критерий положительного случая требует цитату из нужного фрагмента
с `300×300` и отсутствие посторонних статей. Это проверка источника и контрольного
признака; смысловую обоснованность выбранных цитат нужно оценить отдельно. Для
`noise-only` успешен именно `no_evidence`. Локальные тесты используют подстановки модели
и подтверждают работу стенда, а не качество Terra.

`elapsedMs` включает переходы между узлами; точное время вызова и расход токенов
смотреть в spans `Llm.sendRequest`. Сырые ответы и результаты parser сохраняются в
dev-БД под `selector_eval_run:<requestId>`. Для существующего parser создаётся запись
`state:eval:<requestId>`; по завершении пяти повторов удаляется только эта запись.
Прерванный запуск может оставить собственное промежуточное состояние. Отчёты и набор
случаев сохраняются для сравнения. Граф не ведёт к действиям Pyrus или поиску новых статей.

## Воспроизведение набора и обслуживание

Исходные статьи и подготовленный JSON не включаются в Git. Текущий файл находится
в `/tmp` и может быть удалён системой. Набор построен из ранее извлечённых входов:

```sh
node tools/build-selector-eval-cases.js \
  /tmp/pyrus-terra-success-comparison.json \
  /tmp/pyrus-terra-empty-comparison.json \
  /tmp/pyrus-selector-eval-cases.json
```

Если эти временные файлы исчезнут, входы нужно повторно извлечь из исходных трасс,
указанных в [разборе пустого отбора](terra-selector-empty-live-review-2026-09-05.md).
При смене модели или лимита основного Selector обновить определения стенда командой
`node tools/build-selector-eval-graph.js`, затем выполнить `node tests/run.js`.
Проверки обнаруживают расхождение настроек обычного узла и пяти узлов эксперимента.

После первого набора сравниваем частоту полезного и пустого отбора, посторонние цитаты,
токены и время. Затем выбираем следующий эксперимент с промптом или моделью на тех же
входах. При переносе релиза в main dev-триггеры и их привязки переносить нельзя.
