# Сквозная приёмка MVP

Цель приёмки — проверить не отдельные функции, а всю цепочку: реальная модель, статьи БЗ,
MCP, поля Pyrus, создание подзадачи и завершение родительского чата. До завершения этой
проверки форма `1165239` остаётся в режиме `handover_only`, а рейтинговая policy-статья —
черновиком.

## 1. Связь родительского чата и подзадачи

Отдельное поле формы не требуется и поле `95` («Id задачи из КЦ») не используется. Связь
создаётся штатным параметром Pyrus `parent_task_id` в том же запросе, что и подзадача.
После создания бот принимает успех только если Pyrus подтвердил эту нативную связь.

От дублей защищает атомарный claim в `state:<taskId>`. В поле «Сообщение» записывается
стабильный идентификатор текущего обращения: если Pyrus создал задачу, но HTTP-ответ
потерялся, следующий запуск находит именно её среди `linked_task_ids`. Старую подзадачу
переоткрытого чата за новую принять нельзя.

## 2. Подготовка без партнёрских ответов

1. Задеплоить код с `knowledgeExecution: "handover_only"`.
2. Загрузить `docs/knowledge_catalog.json` в документ БД `knowledge_catalog`.
3. Оставить `[RATINGS] Обработка вопросов по рейтингам` черновиком.
4. Проверить, что входящий тикет формы `1096731` игнорируется, а чат `1165239` передаётся
   оператору без отправки найденного ответа партнёру.

## 3. Контроль источников

Непосредственно перед включением повторить живые запросы:

```bash
node tools/kb-mcp-live.js "как подать апелляцию по РКО" "" "" ratings_questions rkoKnowledge
node tools/kb-mcp-live.js "правила апелляции по рейтингу стандартов" "" "" ratings_questions standardsKnowledge
```

Проверка не проходит, если изменились ID, пространство, `updatedAt`, доступность полного
текста или шаблон ссылки хотя бы одного разрешённого источника.

## 4. Управляемое включение

1. Опубликовать рейтинговую policy-статью.
2. В согласованное окно заменить для формы `1165239` только
   `knowledgeExecution` на `partner_answer`.
3. Провести три изолированных разговора реальной моделью.

### Сценарий A — ответ из БЗ и закрытие

- Партнёр пишет по-русски, называет тестовый российский юнит и спрашивает, как подать
  апелляцию по РКО.
- Ответ основан только на прочитанной allowlist-статье.
- Система добавляет предупреждение, рабочую ссылку и вопрос «Эта информация помогла…?».
- До подтверждения чат открыт.
- После явного «да, помогло» заполнены юнит и компонент РКО, выполнен `finished`.

### Сценарий B — ответа нет, создаётся одна подзадача

- Партнёр просит разобраться с конкретным результатом Рейтинга стандартов, причины которого
  нет в общей инструкции.
- Агент не додумывает ответ, собирает ожидаемый результат, применимые детали и email.
- Создаётся ровно одна задача формы `1096731`; повтор события не создаёт вторую.
- В поле «Сообщение» есть юнит, суть, ожидаемый результат, email и собранные детали.
- У подзадачи есть подтверждённая нативная родительская иерархия; поле `95` не изменено.
- Только после этих проверок исходный чат закрывается через `finished`.

### Сценарий C — безопасная граница

- Проверить по одному обращению: просто «рейтинг» без возможности уточнить вид; MD Audit;
  нерусский язык; иностранный юнит; вложение; переоткрытый чат.
- Ни в одном случае нет подзадачи по рейтингу наугад и нет российского partner-facing
  текста. Переоткрытый чат передаётся молча; остальные — по правилам локализованной или
  тихой передачи.

## 5. Условия принятия

Rollout считается принятым, если:

- все локальные тесты зелёные;
- оба live MCP-запроса проходят без drift;
- модель не добавляет фактов вне прочитанных источников;
- партнёрская и внутренняя переписка не смешиваются;
- закрытие невозможно без юнита и компонента;
- подзадача невозможна без email, «Сообщения» и подтверждённой нативной связи;
- повтор webhook не создаёт вторую подзадачу;
- входящие тикеты остаются вне обработки.

После приёмки режим `partner_answer` можно оставить включённым. При любом критическом
расхождении откат не требует деплоя: вернуть `knowledgeExecution: "handover_only"` и
перевести рейтинговую policy-статью в черновик.
