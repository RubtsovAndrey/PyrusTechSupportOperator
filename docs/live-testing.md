# Живые тесты через чат Pyrus

Локальные тесты проверяют функции и граф без сети. Живой тест нужен отдельно: только он
проходит через настоящий web widget Pyrus, вебхук, Agent Platform, LLM, MCP и обратную
запись в чат. Отправка реплик пока остаётся ручной, а разбор результата автоматизирован.

## Один прогон

1. Открыть новый чат в тестовой форме. Каждый сценарий начинается в новой задаче, чтобы
   сохранённый `state:<taskId>` предыдущего разговора не влиял на результат.
2. Посмотреть текст сценария:

   ```bash
   node tools/read-trace.js --list-scenarios
   ```

   Сами реплики находятся в `tests/live/scenarios.json`, поле `messages`.
3. Провести разговор и проверить глазами, что партнёр и оператор увидели ожидаемые
   сообщения.
4. Выгрузить все JSON-трассы разговора в отдельную папку. Исходные трассы не добавлять в
   Git: они содержат текст переписки, идентификаторы задач и другие служебные данные.
5. Из корня проекта запустить проверку:

   ```bash
   node tools/read-trace.js "/полный/путь/к/папке-с-трассами" \
     --scenario unknown-courier-avatar \
     --out result_report.txt
   ```

Скрипт принимает как папку с несколькими JSON, так и один JSON-файл. `result_report.txt`
игнорируется Git. Код завершения `0` означает, что все ожидания выполнены; `2` — что трасса
прочиталась, но сценарий или сама выгрузка не прошли проверку.

Флаг `--prompt` добавляет в отчёт полные запросы к модели. Для обычной проверки он не
нужен: отчёт становится существенно больше и содержит больше данных разговора. Его стоит
включать только при разборе причины падения.

## Что проверяет сценарий

Ожидания описаны рядом с репликами в `tests/live/scenarios.json`. Для каждого витка можно
проверить:

- текст сообщения партнёра;
- исход `applyOutcome`;
- число и содержание ответов партнёру;
- служебные свойства ответа в Pyrus: `action`, `approval_choice` и число обновлённых полей;
- число и содержание внутренних сообщений оператору;
- наличие или отсутствие строк в логах, пути графа и вызовах функций;
- отсутствие ошибок платформы.

Проверка текста нечувствительна к регистру и построена на устойчивых фрагментах, а не на
полном совпадении ответа. Формулировка модели может слегка меняться, но границы поведения —
например, что ссылки из общей БЗ не попали партнёру, — должны оставаться строгими.

## Первый эталон

`unknown-courier-avatar` закреплён по живому прогону от 28 августа 2026 года и обновлён
после того, как широкий MCP-поиск вернул три случайные статьи. Теперь он проверяет, что
неизвестный вопрос об аватарке курьера:

- не получает случайную статью из нашего каталога;
- передаётся оператору;
- запускает `findOperatorKnowledge`;
- не добавляет во внутреннюю переписку материалы, не прошедшие фильтр релевантности;
- не содержит ошибок платформы.

Повторный прогон после деплоя фильтра прошёл `21/21`: MCP вернул девять опубликованных
кандидатов, все они были отсечены, а во внутренней переписке осталось только резюме для
оператора. Это подтверждает отрицательную границу фильтра на всей живой цепочке. Для
положительной границы нужен отдельный первый прогон: неизвестное обращение должно по-прежнему
уйти оператору, но вместе с одной действительно относящейся к вопросу ссылкой общей БЗ.

Первый такой прогон 2 сентября 2026 года нашёл дефект раньше общего поиска: фраза про
принтер этикеток ошибочно попала в `pos_terminal_troubleshooting`, потому что словоформы
`печатает` и `печать` были посчитаны двумя совпадениями с одним корнем кассовой формулировки.
После ответа «это не касса» обращение передалось оператору только вторым витком, поэтому
полезная статья общей БЗ до оператора не дошла. Исправленный эталон закреплён как
`unknown-label-printer-with-relevant-hint`: один виток, неизвестная тематика, статья
«Принтер этикеток» только во внутренней переписке.

В той же трассе две «Ошибки в работе канала» оказались не ошибками Pyrus/MCP-кода, а
`CancellationException: Instance … shutting down`: экземпляр Agent Platform завершался во
время первого витка. Сценарий всё равно обязан считать такой прогон неуспешным — доставка
ответа не доказывает, что перезапуск безопасно завершил все параллельные операции.

Повторный прогон после исправления прошёл `24/24` за один виток и без ошибок платформы.
Внутренний каталог воздержался от кассовой темы, обращение ушло оператору, а общий поиск
добавил только во внутреннее сообщение три осмысленные подсказки из пространств
техподдержки: точную статью «Принтер этикеток», инструкцию по установке принтеров упаковки
и маркировки и статью о настройке кастомного трекинга. Первая статья описывает в excerpt
тот же диагностический признак — этикетки продуктов не печатаются, а тестовая печать
работает. Положительная и отрицательная границы фильтра теперь подтверждены живыми тестами.

Сценарий `known-pos-success-without-component` проверяет предохранитель закрытия. Рабочая
кассовая статья во время первого прогона ещё не задавала `componentName`, поэтому после ответа «Да, помогло» ожидалась
не закрытие, а утверждённая передача оператору: `action` отсутствует, поле известного юнита
заполнено, во внутренней переписке прямо названа причина. Партнёр при этом получает обычное
«Рад был помочь», а не сообщение о дополнительном изучении: проблема уже решена, оператору
осталась только классификация и закрытие. Этот сценарий сохраняется как историческая
проверка предохранителя, но после добавления компонента больше не воспроизводится на рабочем
каталоге.

Для положительного прогона статья использует настоящий компонент Pyrus
`Технический → Для тестов`. Сценарий `known-pos-success-and-close` повторяет те же две
реплики и требует одновременно `approval: approved`, `action: finished`, два обновления
полей, отсутствие внутреннего сообщения и отсутствие ошибок. Это проверяет уже не только
отказ от опасного закрытия, но и полный допустимый контракт закрытия.

Новые сценарии добавляются после первого ручного прогона: сначала сохраняется реальное
поведение, затем в ожидания записываются только важные продуктовые гарантии. Случайные
детали — точное число найденных статей, их порядок или полный текст ответа модели — в
эталон не включаются.

## Тестовый HTML

Локальный `ТЕСТ ЧАТ.html` содержит адрес конкретного Pyrus widget и поэтому намеренно
игнорируется Git. Платформа не должна получать его как ресурс проекта. Если тестовую форму
понадобится переносить между компьютерами, следует добавить в `tools/` шаблон без адреса
виджета, а сам адрес хранить в локальном игнорируемом конфиге.
