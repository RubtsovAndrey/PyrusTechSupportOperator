# Эталонный набор MVP

Статус: утверждено владельцем продукта 3 сентября 2026 года.

Дата: 3 сентября 2026 года.

## Назначение

Набор в `tests/fixtures/mvp-eval-cases.json` фиксирует ожидаемое решение агента, а не
дословный ответ. Для каждого диалога определены маршрут, финальный исход, язык партнёрского
ответа, заполнение юнита и компонента, допустимый источник знаний, необходимость подзадачи,
внутренней сводки и закрытия.

Полные 100 кейсов сейчас проверяются как спецификация решений: тест
`tests/mvp-eval-cases.test.js` контролирует структуру, полноту покрытия, непротиворечивость
политик и отсутствие явных следов исходных задач. Критический маршрут рейтингов уже покрыт
исполняемым end-to-end набором `tests/ratings-dialog.test.js`: ответ из allowlist,
предупреждение и ссылка, подтверждение результата, fallback, сбор email, одна связанная
подзадача, различение двух рейтингов и безопасные отказы. Остальные 100 сценариев
подключаются к диалоговому runner поэтапно; наличие кейса в JSON само по себе ещё не означает
успешную проверку модели. Актуальное число исполняемых проверок печатает сам тест.

## Как набор получен

Использованы повторяющиеся типы обращений из двух августовских выгрузок:

- кассовые чаты и тикеты;
- выбранные компоненты: сотрудники, редактирование карточки, РКО, Рейтинг стандартов,
  MD Audit, Индекс счастья и трудовые вопросы.

Реальные сообщения не копировались. Все тексты сформулированы заново, названия юнитов и
контакты фиктивны, ссылки и номера задач отсутствуют. Исторический ответ оператора не
считается правильным только потому, что он встречался в выгрузке.

## Состав

| Группа | Кейсов | Что проверяется |
|---|---:|---|
| Кассы | 35 | Подготовленные сценарии, уточнения, успех, неуспех и ложные совпадения |
| Рейтинги | 25 | Ответ по одобренной статье, подзадача, обязательные сведения и границы темы |
| Передача оператору | 15 | Известные и неизвестные темы, компонент, общая БЗ и явная просьба человека |
| Язык и рынок | 10 | РФ по умолчанию, иностранный юнит, нерусский язык и отсутствие русского текста |
| Отказоустойчивость | 15 | Формы, переоткрытие, вложения, дубли, гонки и ошибки внешних систем |
| **Всего** | **100** | 25 успешных закрытий, 14 подзадач, 59 передач и 2 игнорируемых запуска |

Число передач намеренно велико: MVP должен уверенно отказываться от неподтверждённого
действия. Рост автоматизации оценивается позже добавлением одобренных тем, а не ослаблением
границ уже описанных сценариев.

## Устройство кейса

- `profile` содержит общее ожидаемое решение для класса сценариев;
- `messages` — только сообщения партнёра по порядку;
- `context` задаёт форму, переоткрытие, вложение, тестовый юнит или способ доставки события;
- `services` моделирует найденный ответ БЗ либо контролируемую ошибку внешней системы;
- `expect` меняет отдельное ожидание профиля для конкретной границы.

Точные фразы ответа не закрепляются. Будущий runner должен оценивать смысл и обязательные
действия: например, что предупреждение и ссылка присутствуют, русская строка не ушла в
английский чат, подзадача содержит поле «Сообщение», а чат действительно остался открытым
после сбоя.

## Утверждённые решения

1. Очевидные темы без самостоятельного решения получают компонент до передачи оператору:
   карточка сотрудника, сотрудники, MD Audit, трудовые вопросы и Индекс счастья.
2. Обращения об оплате картой и кассовом расхождении получают соответствующий компонент,
   но не получают кассовую инструкцию из другой ветки.
3. Несогласие с результатом **MD Audit** остаётся обычной передачей оператору. В единый
   сценарий подзадачи входят только РКО и Рейтинг стандартов.
4. Если партнёр говорит просто «рейтинг», агент уточняет вид. После двух безрезультатных
   попыток он передаёт чат оператору, потому что безопасно выбрать один из двух компонентов
   подзадачи невозможно.
5. Найденный ответ по рейтингу закрывает чат только после явного подтверждения партнёра и
   при наличии подтверждённого юнита и компонента.
6. Сценарии, помеченные `knowledge: approved_answer`, проверяют ветвление при наличии
   подходящей одобренной статьи. Для рейтингов четыре источника уже закреплены в allowlist и
   проверены живым MCP-чтением; соответствие конкретного ответа тексту источника всё равно
   требует прогона реальной модели перед публикацией.

Если партнёр подтвердил успех, но юнит или компонент не определён, `finished` не вызывается:
задача тихо передаётся оператору, и дополнительное обещание о закрытии партнёру не
отправляется.

Изменения содержания статей будут проверяться отдельно: эталонный набор не должен
незаметно менять бизнес-политику вслед за текстом Базы знаний.

## Запуск проверки набора

```bash
node tests/mvp-eval-cases.test.js
```

Полный локальный прогон включает эту проверку через `node tests/run.js`.
