# Архитектура знаний и правил обработки обращений

Принято 2026-08-28. Этот документ фиксирует целевую модель, чтобы слова «единый источник
правды» не смешивали редакторское хранение, поиск и исполняемый runtime.

## Главный принцип

**База Знаний — редакторский источник правды. `knowledge_catalog` — проверенный runtime-
снимок, собранный из неё.** Снимок не является вторым местом редактирования: его нельзя
править руками, как нельзя править собранный файл вместо исходника.

Прямой MCP-поиск не принимает решение о маршруте самостоятельно. Он может:

- читать наше пространство во время синхронизации;
- после неудачного поиска по локальному каталогу вернуть маршрутизатору не более двух
  опубликованных policy-статей из нашего пространства как кандидатов;
- читать конкретную статью, которую разрешил утверждённый сценарий;
- подбирать оператору возможные материалы, если утверждённого сценария нет.

Кандидат, совпавший с `excludedEvidence`, отбрасывается ещё до модели. Остальной кандидат
из MCP даёт право ослабить только отсутствующую буквальную группу `requiredEvidence`,
например код «148», когда другая группа уже подтверждена словами партнёра — «чек» или
«реквизит». Для этого полный блок `agent-topic/1` опубликованной статьи
должен в точности совпасть с текущей темой `knowledge_catalog`. Решение всё равно принимает
маршрутизатор по контексту разговора, а область применения и `excludedEvidence` остаются
жёсткими ограничениями. Подтверждение привязано к одному входящему комментарию и затем
истекает. Поэтому MCP помогает распознать другую формулировку уже утверждённого сценария,
но не может незаметно добавить новый сценарий или изменить бизнес-действие.

## Два вида знания

### Политика обращения

Живёт только в нашем пространстве и определяет:

- когда сценарий подходит (`description`, `phrasings`);
- исход: ответ, подзадача или оператор;
- какие данные обязательно собрать;
- компонент подзадачи;
- можно ли использовать общую БЗ;
- что делать при неуспехе.

Текущий формат — `agent-topic/1`: `route`, `article`, `steps` или `nodes`. Следующая версия
должна отдельно назвать способ обработки и источник знания, не меняя поведение существующих
статей.

### Предметное знание

Обычные статьи нашего или чужого пространства: инструкции, справочники, описание продукта.
Они могут дать текст ответа, но не могут сами решить, закрывать чат, создавать подзадачу
или передавать обращение.

## Безопасные правила runtime

1. Сначала ищется утверждённая политика в runtime-каталоге.
2. Если буквальный поиск не дал уверенного результата, маршрутизатор может сделать не больше
   двух MCP-запросов в наше пространство и выбрать только полностью прочитанную,
   опубликованную policy-статью, совпадающую с тем же runtime-каталогом.
3. Есть уверенно выбранная политика — исполняется только она и разрешённые ею источники.
4. Политики нет — обращение передаётся оператору.
5. Перед такой передачей разрешён поиск по всей доступной БЗ. До трёх опубликованных и
   прошедших фильтр релевантности результатов добавляются во внутреннюю переписку:
   заголовок, пространство, excerpt и ссылка. Наше пространство имеет первый приоритет,
   пространства техподдержки — второй, остальная БЗ — третий. Копии с одинаковым заголовком
   показываются один раз.
6. Эти результаты не показываются партнёру и не меняют решение о handover. Изолированный
   `Operator Assist Composer` может построить по переписке и отфильтрованным excerpt один
   явно неотправленный черновик первого ответа для проверки оператором.
7. Недоступность MCP или сбой Composer не блокируют handover.

Запасной лексический подбор утверждённой политики использует только `phrasings`: для
многословного обращения нужны минимум два совпадения внутри одной формулировки.
`description` может описывать ограничения темы и поэтому не считается положительным
лексическим сигналом.

Текущая реализация пунктов 4–6: `ID_Tools.findOperatorKnowledge`,
`agent_operator_assist` и `ID_Tools.parseOperatorAssist`. Эта цепочка стоит только на
отрицательной ветке маршрутизации (`cond_routing_subtask → func_find_operator_knowledge`).
Просьба человека, вложение, ошибка агента и handover по известной статье поиск не запускают.
`search_content` не отдаёт оценку релевантности и работает как широкий генератор кандидатов.
Поэтому функция сама отбрасывает совпадения только по общим словам: для многословного
запроса нужно значимое слово в заголовке или минимум два значимых слова в excerpt. Если
ничего не прошло, оператор получает обычную сводку и неотправленный черновик без блока
возможных материалов. Parser удаляет добавленные моделью URL и при любой ошибке оставляет
обычную передачу работоспособной.

## Публикация

Статья в БЗ и версия знаний бота публикуются отдельно:

1. Сценарий пишется и проверяется в черновике БЗ.
2. Опубликованные статьи синхронизируются командой `node tools/sync-kb.js` в режиме
   предпросмотра, затем с `--write`.
3. `node tools/build-knowledge.js` собирает каталог и манифест с хешами.
4. `node tests/run.js` проверяет формат, маршруты, конкретные статьи и полные диалоги.
5. Человек просматривает дифф и диалоги.
6. Только после этого новый `knowledge_catalog` загружается в Agent Platform.

На первом этапе шаг 6 ручной. Это позволяет выпустить знания полуавтоматически и сохранить
предыдущий снимок для отката без отдельного сервиса.

### Приёмка ответа, связанного с общей БЗ

Сценарий, который отвечает партнёру по общей статье, может хранить карточку `validation`:
статус приёмки, закреплённые `articleId`, заголовок раздела, дату изменения источника и два
SHA-256 — самого раздела и разрешённого исполняемого ответа. Проверка одной карточки:

```bash
node tools/validate-knowledge.js cash_shift_over_24_hours --show
```

Команда ничего не меняет: читает закреплённую статью через MCP, показывает исходный раздел
рядом с ответом бота и завершается с ошибкой при любом дрейфе. Новый хеш не означает, что
изменение верно: после изменения источника сценарий повторно проверяет человек, и только
затем обновляются дата и хеши карточки.

Runtime-проверка решает другую задачу. `searchKnowledge` выдаёт разрешение на решение только
для текущего комментария партнёра. Если модель попробует написать решение после ответа
инструмента без `solverInstruction` или повторно использовать решение прошлого витка,
`parseAgentJson` удалит текст и передаст обращение оператору.

## Подзадачи

Подзадача создаётся только из чата и сама является тикетом. Из тикета новая подзадача не
создаётся. Сценарий обязан заранее определить компонент и собрать данные, нужные внешней
команде; `createSubtask` проверяет этот контракт перед созданием.

## Тестовый корпус

Каждый новый сценарий добавляет:

- положительные формулировки в `tests/routing.cases.json`;
- отрицательные формулировки близких, но чужих проблем;
- полный разговор с ожидаемым исходом `self_service`, `subtask` или `handover`;
- при необходимости — ожидаемые поля и компонент подзадачи.

Разговоры, которые вручную разыгрываются при приёмке, переносятся в тесты и становятся
регрессионным корпусом. Персональные данные в нём заменяются тестовыми.

## Следующие расширения

1. Ввести обратно совместимую схему политики следующей версии: отдельно `handling`,
   `knowledge` и `fallback`.
2. Распространить карточки `validation` и проверку закреплённых внешних статей на остальные
   сценарии, которым разрешён прямой ответ партнёру.
3. Разрешать автоматический ответ из общей БЗ только явным полем политики.
4. Записывать в состояние задачи версию каталога и использованные источники.
5. После накопления корпуса оценить качество на живых обращениях в shadow-режиме.
