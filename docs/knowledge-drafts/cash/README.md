# Кассы: проект policy-слоя первой версии

Статус: исторический проектный слой и тестовая матрица. Три принятых сценария перенесены
в исполняемые `agent-topic/1`-темы и 2 сентября 2026 года опубликованы в пространстве
«ИИ Техподдержка - Конфигурация». Последующие загрузка каталога, деплои и живые прогоны уже
выполнены; актуальное состояние ведётся в
[`current-project-status.md`](../../current-project-status.md), а исполняемые источники — в
[`docs/knowledge/topics`](../../knowledge/topics/).

## Зачем нужен отдельный слой

Общая БЗ остаётся источником фактов и инструкций. Наши статьи определяют не содержание
общей БЗ заново, а условия безопасного применения знания: какой сценарий распознан, какие
факты обязательно получить, какую статью разрешено использовать, что спросить после
совета и когда передать чат оператору.

Текущий импорт понимает только `agent-topic/1`. В черновиках используется
`agent-policy/2-draft`: это сознательно неисполняемая схема, чтобы материалы нельзя было
случайно включить в прод до реализации и приёмки нового контракта.

## Общий кассовый пузырь

Пузырь `cash` — это область маршрутизации, а не одна большая инструкция. Внутри него
выбирается ровно один узкий сценарий. Если доказательств для сценария недостаточно, бот
уточняет факты, но не смешивает советы соседних веток.

Порядок работы:

1. Убедиться, что известен полный юнит. Взять домен бизнеса и страны из префикса полного
   имени (`[dodopizza.ru]`, `[dodopizza.by]`, `[dodopizza.com.cy]`); не определять страну
   по городу и не спрашивать юнит повторно, если он уже однозначно указан в чате.
2. Уточнить тип кассы: ресторан или доставка, если он влияет на компонент или инструкцию.
3. Уточнить точное проявление проблемы. Текст ошибки важнее общего слова «касса».
4. Проверить стоп-условия сценария и актуальность закреплённого источника.
5. В тестовой форме вести разговор так же, как в будущем на проде: по известному сценарию
   отправить закреплённый совет партнёру и спросить о результате.
6. Писать во внутреннюю переписку только при передаче оператору: положить туда сводку,
   собранные факты, уже отправленные советы и найденные статьи.

## Общий контракт `agent-policy/2-draft`

- `rollout`: режим отдельно для тестовой и продуктивной формы. Сейчас тестовая форма
  использует `partner_answer`, продуктивная — `off` до отдельного решения.
- `scope`: точные домены бизнеса и страны и типы касс, для которых проверено решение.
- `match`: достаточные признаки и явные исключения.
- `requiredFacts`: факты, без которых совет запрещён.
- `classification`: компонент по типу кассы. `null` означает блокер публикации.
- `sources`: закреплённые статьи, дата проверенной версии и обязательные смысловые
  фрагменты. Если статья изменилась и фрагмент пропал, ответ блокируется.
- `resolution`: один совет, вопрос проверки результата, успешный и неуспешный исходы.
- `safety`: действия, которые нельзя предлагать партнёру.

## Контракт текущего теста

Внешняя переписка:

- бот уточняет отсутствующие юнит, тип кассы и необходимые признаки сценария;
- по известному сценарию отправляет решение партнёру и спрашивает, помогло ли;
- при успехе заполняет юнит и компонент и закрывает чат;
- при неуспехе или стоп-условии сообщает о передаче обращения специалисту.

Внутренняя переписка:

- при успешном решении внутреннего сообщения нет;
- при передаче: краткая формулировка проблемы, собранные факты, выбранный сценарий или
  причина отказа, уже отправленные советы, названия и ID найденных статей, юнит и компонент.

## Правила источников

- Поиск по всей общей БЗ разрешён для внутреннего черновика ответа на неизвестный вопрос.
- Внешний ответ по известному сценарию строится только по закреплённым источникам.
- Внутренние операторские инструкции, удалённый доступ и действия с файлами/портами не
  превращаются в партнёрский совет без отдельного разрешения.
- Первая пачка кассового пузыря разрешена только для точного домена `dodopizza.ru`.
  `dodopizza.by`, `dodopizza.com.cy`, другие домены Dodo Pizza и `drinkit.ru` не получают
  эти инструкции. Для каждой страны можно завести отдельную policy с её доменом; новое
  поле страны в каталоге для этого не требуется.

## Где хранить знания

Рекомендуемая модель — служебные статьи в нашем пространстве БЗ, по одной статье на
сценарий с общим тегом `[CASH]` в названии:

- общая БЗ хранит исходные факты и инструкции для партнёров;
- наше пространство БЗ хранит надстройку: признаки сценария, обязательные вопросы,
  исключения, компонент, разрешённый текст ответа, проверку результата и ID источников;
- репозиторий хранит синхронизированную проверенную копию и сгенерированный каталог для
  Agent Platform, но не становится вторым независимо редактируемым источником;
- обычная БД хранит только оперативные данные: `unitCatalog`, роли/окружение форм и
  разрешённый режим исполнения. Сами инструкции в БД не дублируются.

Для безопасного rollout нужны два независимых разрешения. Статья сообщает статус сценария
(`testing` или `approved`), а конфигурация формы сообщает окружение (`test` или
`production`). Тестовая форма может выполнять `testing`-сценарии как `partner_answer`;
продуктивная форма — только `approved`. Так публикация черновой статьи сама по себе не
откроет ответы на проде.

Пример будущего расширения существующего документа конфигурации форм:

```json
{
  "forms": {
    "2430464": {
      "role": "chat",
      "environment": "test",
      "knowledgeExecution": "partner_answer"
    },
    "2454249": {
      "role": "ticket",
      "environment": "test",
      "knowledgeExecution": "handover_only"
    }
  }
}
```

Конкретные ID продуктивных форм в этот пример намеренно не добавлены.

## Что следует из текущих тестов

Существующие live-сценарии уже проверяют правильную механику:

- известный совет: внешнее сообщение, внутренних сообщений `0`;
- «помогло»: юнит и компонент заполняются, задача утверждается и закрывается, внутренних
  сообщений `0`;
- «не помогло»: внешняя отбивка о передаче и одно внутреннее резюме со сделанными шагами;
- неизвестная тема: уточнение недостающих фактов, затем передача и одно внутреннее резюме
  с подходящими статьями общей БЗ.

Текущую широкую тему `pos_terminal_troubleshooting` нельзя целиком переключать из
`operator_hint` в `partner_answer`: это одновременно разрешит внешние советы для ещё не
принятых JavaScript, DNS, соединения с ККМ и терминала. Для теста нужно сначала вынести
три выбранных сценария в независимые исполняемые темы либо добавить branch-level rollout.

## Исторический план первого теста на платформе

Пункты 1–3 ниже завершены после создания этого черновика; они сохранены как история
первого rollout, а не как текущий список задач:

1. В документе БД `config` разрешить `partner_answer` только тестовой форме `2430464`.
2. Загрузить собранный `docs/knowledge_catalog.json` в одноимённый документ БД.
3. Задеплоить код и прогнать сценарии в тестовой форме; по трассам определить порог
   приёмки.
4. Проверку версий закреплённых источников реализовать через карточки `validation` и
   `tools/validate-knowledge.js`; распространение этих карточек на новые сценарии остаётся
   частью дальнейшей работы перед продуктивным rollout.

## Компоненты пузыря

- касса ресторана → `Касса → Касса ресторана → Печать чека`;
- касса доставки → `Касса → Касса доставки → Печать чека`.

Это правило применяется ко всем сценариям кассового пузыря, а не только к печати чека.
